# Relay Privacy Policy Requirements

本書は、[PallaSync Protocol 3.0](./v3.0.md) §17.12 に対応する、リレー運用者の `privacy.md` の必須開示要件です。本書には特定の運用者の quota、バックアップ間隔・保存期限、コピー保持期間、削除保証の実値は含まれていません。運用者は、実際の設定と約束を記載した独自の `privacy.md` と署名付き `privacy.json` を公開しなければなりません。本書をそのまま公開しても、実運用の開示を完了したことにはなりません。

MUST / MUST NOT / SHOULD / MAY は v3.0.md の規定に従います。以下はプロトコルの運用・実装要件であり、ポリシーへの同意によって E2EE、鍵保護、保持、認可、削除検証の規則を緩和することはできません。

## 公開場所と適用範囲

運用者は、各 `relay_origin` の HTTPS URL `${relay_origin}/privacy.md` で、その origin に適用される運用者固有のポリシーを公開することを **MUST** とします。これは `/pallasync/v3/` の認証 API とは別の公開文書です。同じ origin の `${relay_origin}/privacy.json` にも §7.13 の `RelayPrivacyDisclosure` を公開し、`application/json`、復号後最大1 MiB、匿名取得とします。両文書は同じ現行版を表し、JSON の `markdown_sha256` が Markdown の厳密な本文 bytes と一致しなければなりません。取得に Capability Token、chain_id、device_id、アカウント、Cookie、アプリ固有の認証情報を要求してはなりません。

応答は `200`、`Content-Type: text/markdown; charset=utf-8`、有効な UTF-8 の Markdown とし、本文は HTTP Content-Encoding の復号後で最大 1 MiB とします。クライアントは他 origin へのリダイレクトを追従してはなりません。同一 origin の条件付き取得と `304` は、検証済みの同一文書キャッシュがある場合に限り使用できます。公開文書へのレート制限もポリシーで開示し、同意確認のための取得を可能にしなければなりません。

ポリシーには、次の識別情報をすべて記載することを **MUST** とします。

| 項目 | 必須内容 |
|---|---|
| 運用者 | 名称と、問い合わせ・障害・削除依頼に利用できる連絡方法。利用者アカウントを必須にしないこと。 |
| 適用 origin | 正規化された HTTPS origin の一覧。移行先候補を記載しても、その origin に対する同意や権限移転を意味しないこと。 |
| ポリシー版 | 固定の版識別子、公開日時、適用開始日時。日時には UTC または明示的な UTC offset を付けること。 |
| 変更方法 | 改版の告知方法と告知時期、過去版の確認方法。内容を変えた場合は必ず版識別子を更新すること。 |
| relay key の運用 | attestation 鍵を独立に生成・保護する方法と、予定する手動交換・告知・旧署名証拠の保持手順。秘密鍵や保管先の認証情報は公開しないこと。自動 rotation が定義されていないこと、交換には明示的な信頼再確立と再同意が必要なこと。 |

## quota と容量

| 項目 | 必須内容 |
|---|---|
| 保存容量 | 適用される `max_bytes` の実値と byte 単位、課金・設定区分がある場合は各区分の実値と適用条件。quota を設定しない場合は `max_bytes = null` とその意味を明記すること。 |
| 計上対象 | イベント、snapshot、envelope、署名付き receipt、透明性ログ、メタデータ、バックアップ等のうち何を quota に計上するか。重複・レプリカの計上方法。 |
| 上限到達 | 新規書き込みの停止条件、`507 QUOTA_EXCEEDED`、復旧・増量・安全な compaction・移行の方法。受理済みデータを黙って削除しないこと。 |
| リクエスト制限 | 実際のサイズ、レート、同時実行制限。`429` と `Retry-After` の扱い。既定値より厳しい設定はすべて開示すること。 |
| 保存とサービス終了 | 利用停止・休眠・契約区分変更・サービス終了時のコピー保持、書き込み停止、export の提供条件。プロトコルの保持・削除規則に適合すること。 |

`max_bytes = null` は quota を設定しないという意味であり、無限容量・無料・永久保存・可用性保証を意味しません。利用量 `used_bytes` は認証された API で扱い、公開ポリシーに個別チェーンの識別子や利用量を掲載してはなりません。チェーンごとに quota が異なる場合は、適用規則を事前に開示し、クライアントが取得した実値を利用者に表示できるようにしなければなりません。

## バックアップ

| 項目 | 必須内容 |
|---|---|
| durability tier | `single-durable`、`replicated-durable`、`backup-durable` のいずれかと、その実際の障害境界。`GET /health` の表示と一致すること。 |
| 実施の有無 | バックアップを実施しない場合は、その旨と復旧不能になる障害範囲を明記すること。 |
| 間隔 | 実施する場合は実際の最大実行間隔、許容される復元時の巻き戻り範囲、失敗した場合の告知・復旧方法。 |
| 保存期限 | 各バックアップ階層の最大保持期間、期限の起算点、期限到達時の削除・鍵破棄方法。 |
| 保存場所 | 保存地域、別障害ドメイン・別運用者の利用有無、委託先の役割。非公開の物理配置や認証情報まで掲載する必要はない。 |
| 保護と復元 | 運用者側の保存用暗号化と鍵管理、復元時の deletion ledger 照合、旧 `log_id` / 透明性ログとの整合性確認。 |
| 復元試験 | 実際の試験間隔と直近の成功日時。 |

`backup-durable` の「少なくとも毎日バックアップ」「少なくとも90日ごとに復元試験」という v3.0.md §17.1 の既存条件は維持されます。プロトコル全体で一律の実間隔・保存日数を新たに設定するものではありません。バックアップを実施しない場合の保存期限は「対象なし」と記載でき、単に値を省略してはなりません。

## operator のコピー保持

運用者は、次の各分類について、作成の有無、目的、保存場所・委託先、アクセス可能な主体、最大保持期間または明示的な保持終了条件、削除・鍵破棄方法を開示することを **MUST** とします。

- 稼働中ストア、レプリカ、WAL、snapshot store。
- 通常・災害復旧用バックアップ。
- import / restore / migration の staging コピー。
- export、サポート、調査で作成する一時コピー。
- キャッシュ、監視・アクセス・障害ログ。
- UploadReceipt、透明性ログ、削除後の最小 deletion ledger と公開認可証拠。

コピーが存在しない分類は「作成しない」と明記します。チェーン削除まで保持する場合はその終了条件を明記します。技術上必要な最小削除台帳等を無期限で保持する場合は、保持するフィールド、理由、アクセス制限を具体的に開示します。削除対象の ciphertext と、復活防止のために残す最小公開証拠を区別しなければなりません。

受理済み履歴の保持を自動期限削除へ変更したり、root material、Recovery Share / RMS / RSWK / RecoverySecretBlob、Capability Token を保存したりする許可として、このポリシーを使ってはなりません。診断目的であってもプロトコルの禁止事項は維持されます。

## 削除保証

| 項目 | 必須内容 |
|---|---|
| assurance | 実際に提供する `crypto-shred` または `backup-expiry` と、その適用条件・対象外。 |
| 対象 | 稼働コピー、レプリカ、snapshot、envelope、staging、一時 export、バックアップ、委託先コピーの各扱い。 |
| 期限 | 削除受理後の稼働コピー処理期限と、各残存コピーの最終削除・鍵破棄までの最大期限。起算点を明記すること。 |
| 鍵破棄 | `crypto-shred` では運用者側保存鍵、KMS の旧版、バックアップ鍵コピー等の扱い。E2EE 鍵を消すという説明にしないこと。 |
| 完了と証拠 | `requested_at_ms`、`completed_at_ms`、`delete_after_ms` の意味、DeleteReceipt の取得方法、残る最小台帳・認可証拠。 |
| 限界 | 利用者・失効端末・攻撃者が保持したコピーを消せないこと、運用者署名が物理消去を証明しないこと。 |

`backup-expiry` を提供する場合は、有限の最大期限を開示し、削除 receipt の `delete_after_ms` に具体的な期限を設定することを **MUST** とします。期限を約束できないバックアップに対してこの assurance を宣言してはなりません。`crypto-shred` も、運用者側暗号化を外れた削除不能なコピーがある状態では成立しません。

削除後の最小台帳・証拠の保持は、チェーンを再登録・復活・書き込み可能にする権限ではありません。未検証の `410` やポリシーに書かれた削除通知から、クライアントのデータ・鍵を自動消去してはなりません。

## 観測するメタデータと利用目的

v3.0.md §14.5 の観測可能なフィールドに加え、実際に保持する IP、User-Agent、時刻、接続・エラー情報等について、収集項目、目的、保存期限、委託・外部提供の有無を記載することを **MUST** とします。保持しない項目はその旨を記載します。E2EE を理由にメタデータも見えないと説明してはなりません。公開 policy の取得自体も接続メタデータを発生させることを記載します。

## クライアントでの必須同意

クライアントは v3.0.md §11.7 に従い、各 origin の現在の両文書を毎リクエスト前に再検証し、構造化値と完全な Markdown ポリシーを表示し、明示的な肯定操作による同意を得ることを **MUST** とします。

- 初回利用、enrollment、初回復元、relay 移行では、同意前に chain API を呼ばず、Capability Token、チェーン識別子、ciphertext、export を送信しません。選択された origin への匿名 health / policy 取得だけを許可します。
- 同意は正規化した origin、検証済み `relay_key_id`、取得した本文 bytes の SHA-256、完全な署名付き disclosure の JCS SHA-256 と revision に紐づけます。別 origin や別鍵、変更された本文へ流用しません。
- 同意ボタン・チェックは既定で未選択とし、初期設定、無操作、タイムアウト、アプリ更新、バックグラウンド処理を同意として扱いません。
- Markdown または構造化 disclosure が変わった場合は、改版・内容を表示して再同意を要求します。版文字列が同じでも、本文ハッシュが違えば以前の同意は使えません。
- 拒否・撤回・未回答では対象 relay への chain API を停止し、ローカルデータ、鍵、outbox を保持します。ローカル閲覧・編集・export は可能です。
- policy が取得できない、不正な UTF-8、上限超過、他 origin への誘導、未確認の本文である場合は同意待ち／取得待ちとして停止します。鍵削除、無条件再登録、別 relay への自動追従で回復しません。

同意記録は端末ローカルの保護ストレージに置き、同期・relay 送信・公開 audit の対象にしません。利用者は同意した版・本文、日時、origin を確認し、撤回できなければなりません。撤回は relay 側データの削除ではなく、削除には既存の明示的な認可・検証手順が必要です。

同意は、この文書の開示事項を利用者が選択したというローカル記録です。運用者が記載どおりに保存・削除したことを暗号的に証明しません。

## 必須機能と選択可能な設定

v3.0.md §12.3 の選択範囲を、クライアントの設定・同意画面と運用者のポリシーで正確に表示することを **MUST** とします。

| 項目 | 必須実装・選択可能な範囲 |
|---|---|
| Shamir Recovery | すべての3.0準拠クライアントで実装必須。未提供の実装は準拠を主張できない。新規チェーンのセットは `not_provisioned` とし、作成・配布・復旧は明示的な同意と操作を必要とする。 |
| t/n | 既定は2-of-3。2-of-4、3-of-4、3-of-5等の有効構成は同じprofileを使う。作成画面で提示する構成は設計・UI判断だが、復旧は有効なprofile構成を扱えること。構成変更ではセット全体を再生成する。 |
| ローカル表示・キャッシュ | 狭い表示範囲や小さいbodyキャッシュを選べる。論理保持・検証済み件数、同期projection、ローカル表示・キャッシュ範囲を区別する。キャッシュ削除は論理削除ではない。 |
| rate limit / quota | 固定されたプロトコル上限を増やせない。運用者はより厳しい設定を選べるが、実値・適用範囲・停止条件を利用前に開示し、クライアントの同意対象にする。 |
| durability tier | 指定された3種から正確に1つを選び、その要件を満たして広告する。選択と実際のバックアップ・障害境界は開示事項。 |
| relay key | 独立した生成・保護が必須。自動rotationは未定義。ポリシー同意だけで新しい鍵を信頼せず、明示的な信頼再確立と新しいorigin/keyへの同意を必要とする。 |

Shamir Recoveryのセット作成同意、初回信頼源の選択、relayポリシーへの同意は、異なる対象に対する操作です。一方の肯定操作を他方への同意に流用してはなりません。

## 初回復元とプロトコル上限

ローカル pin も既知 peer もない初回復元では、クライアントは v3.0.md §11.6 の信頼源選択を別途要求します。ポリシーへの同意を checkpoint / snapshot への信頼とみなしてはなりません。利用者が選択した source にも、署名・鍵・chain_id・履歴・AEAD・snapshot 検証を適用します。

運用者ポリシーは、3.x の snapshot 上限 65,536 parts や既存整数・Palleria `/3` 外部 ID の表現を拡張しません。完全 snapshot が収まらない場合は log を保持・再生し、不完全 snapshot を完全なものとして扱ったり、その prefix を prune したりしてはなりません。将来の表現変更は v3.0.md §0 と Open Question OQ-05 に従う別の仕様・版決定を必要とします。

## 機械可読な署名付き開示

`privacy.json` は任意の補助資料ではなく、すべてのリレーに必須です。正確なフィールド・条件は [v3.0.md](./v3.0.md) §7.13 と [privacy.schema.json](./privacy.schema.json) に従います。すべての適用フィールドは必須で、対象外は `enabled:false` / `present:false` / 規定された `null` とし、未定の自由文で数値欄を代用しません。

- durability tier と health の同名 limits は実設定と一致させます。
- quota の範囲、未設定の可否、計上対象、割当規則、5種類の rate-limit scope の実値を記載します。
- backup の最大間隔、保存終了条件、復元試験間隔・直近成功日時、全12 copy class の有無・保持・削除期限を記載します。有限期限は整数 millisecond、保持の起算点は §7.13 に従います。
- deletion assurance、稼働コピー・backup・鍵破棄期限、relay key 保護と明示的な信頼再確立による交換、replay cache の方式を構造化します。restart barrier 方式なら60秒の基準、許容 clock skew、連携・復旧手順と繰返し再起動で遅延が延びることを本文でも説明します。
- 独立 relay key で `PALLASYNC-RELAY-PRIVACY-v3\0` と自身の `relay_signature` を除いた JCS を署名します。署名は Markdown hash を含むすべての宣言値を保護します。

クライアントは strict JSON profile、スキーマ、URL と canonical binary encoding、§7.13 の条件間整合性、署名、選択 origin/key、本文 hash、版の単調性を検証します。必須項目欠落、署名不正、health/quota との可視的な矛盾、版の巻き戻りでは `C_RELAY_DISCLOSURE_INVALID` としてオンライン操作を停止し、鍵・ローカル状態・outbox と公開証跡を保持します。公開時の文書組合せ競合は両方を限定回数再取得でき、未検証のまま送信しません。

以前の Markdown のみへの同意は十分ではありません。利用者の明示的な肯定操作によって両文書・版・origin/key に紐づけた同意を新しく取得し、以後の変更でも再同意を必須とします。relay key の変更には同意とは別の信頼再確立を要します。

JSON の構造検証は必須項目と形式・関係を検査するものです。自然文の真実性、運用者の実際の保存・物理消去までは検証できません。Markdown は copy のアクセス・保護・具体的交換手順等の人間向け詳細として引き続き必須で、JSON と矛盾してはなりません。本書にも JSON Schema にも、特定運用者の実値を推測して埋めた稼働用 `privacy.json` は含めません。Appendix C.11 の値は公開テスト専用です。
