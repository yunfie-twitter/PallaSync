# PallaSync Protocol 3.0

- Document ID: `PALLASYNC-3.0-R1`
- Protocol identifier: `pallasync/3`
- Protocol version: `3.0`
- Status: Draft Standard
- Supersedes: `PALLASYNC-2.1-R2` (PallaSync Protocol 2.1)
- Default media type: `application/vnd.palleria.sync.v3+json`
- Error media type: `application/problem+json` (RFC 9457) with PallaSync extension members
- Export media type: `application/vnd.palleria.sync.export.v3+jsonl`
- API base path: `/pallasync/v3/`
- Character encoding: UTF-8
- JSON profile: I-JSON (RFC 7493) restricted as defined in §3; canonicalization by JCS (RFC 8785)
- Transport: HTTPS only (TLS 1.2 or later; TLS 1.3 RECOMMENDED by deployment, see §17.1)
- Security model: Accountless, End-to-End Encrypted (E2EE), Capability-based access, epoch-based key rotation
- Normative terms: **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, **OPTIONAL** are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when, and only when, they appear in bold or all capitals.

> [!IMPORTANT]
> This document is normative for PallaSync Protocol 3.0. Where README files, implementation notes, comments, or server configuration contradict this document, this document prevails.
>
> Implementers MUST use vetted cryptographic libraries. Cryptographic primitives MUST NOT be implemented ad hoc. The pure reference computations used to produce the test vectors in Appendix C are for verification only and MUST NOT be shipped.

> [!NOTE]
> **Use of SHOULD in this document.** Every **SHOULD** in this document is accompanied by the concrete consequence of not following it. Behaviour required for interoperability, security, or convergence is always stated as **MUST**. Implementations that deviate from a **SHOULD** remain conformant and interoperable.

## 0. Versioning Decision

**Decision: this revision is published as `PallaSync Protocol 3.0` (protocol identifier `pallasync/3`).**

The revision brief allowed `2.2` only if wire format, ciphertext format and API responses stayed compatible with 2.1. The required fixes cannot be delivered under that constraint. Each of the six categories named in the brief needs a breaking change:

| Category | Breaking change required | Why it cannot be done compatibly |
|---|---|---|
| Record format | `collection_name`, `action`, `lamport`, `created_at_ms` removed from the plaintext envelope; `collection_tag` added; `record_id` changes from UUIDv7 to UUIDv4 | 2.1 servers validate and 2.1 clients read these envelope fields. Removing them is the only way to stop the server from seeing them (§14). |
| AAD | `RecordAAD` changes type tag, field set, and adds `collection_tag` | A 2.1 client would compute a different AAD and get an AEAD failure on every 3.0 record. |
| Key derivation | `epoch_key = HKDF(prk, epoch 0)` replaced by random per-epoch secrets delivered in envelopes; the chain salt becomes deterministic | Keys derived deterministically from the mnemonic cannot be rotated away from a device that already holds them (§13.1). A 2.1 client cannot get the new keys. |
| Capability Token | `v: 3`, adds `aud` and `signer_kind`, allows admin-signed tokens | Multi-relay deployments need audience binding to stop token replay across relays. Mnemonic-only recovery needs admin-signed tokens. |
| HTTP API | New base path `/pallasync/v3/`; new resources (epochs, envelopes, log, snapshots, export, enrollment); RFC 9457 error bodies; `DELETE` needs admin authority by default | The 2.1 response shapes (bare arrays, untyped `rejected`) cannot express the required error model. |
| Conflict resolution | The comparison key gains an operation rank (delete wins on a Lamport tie); per-op Lamport stamps; collection-scoped `clear`; deterministic eviction floors | Under the 2.1 rules, 2.1 and 3.0 clients would reach different final states for the same input. |

Consequences:

1. A 3.0 chain is a **new chain** with a different `chain_id`. It is created from the **same 24-word mnemonic** (§9). 2.1 clients never see 3.0 records, because they use a different base path and a different `chain_id`. This avoids the 2.1 behaviour of purging keys on `410 Gone` being triggered by an upgrade.
2. The four invariants below are unchanged from 2.1. They are restated as normative requirements in §2.1:
   - Accountless design.
   - A 24-word BIP39 mnemonic plus its optional passphrase as the sole source of root authority; direct mnemonic entry remains the default recovery method (§5.6).
   - The server as a blind relay with no decryption capability.
   - E2EE, Ed25519 signatures, AEAD encryption, and Capability-Token authorization as the basic model.
3. Minor versions `3.x` MUST stay wire-compatible with `3.0`. Extensions MUST use the `ext` member (§3.6) or new collections. Any change to the six categories above requires `4.0`. In particular, a 3.x extension MUST NOT raise the existing 65,536-part snapshot ceiling or the integer bounds, or reinterpret current Palleria `/3` numeric ID fields to accept larger values. Operator policy, ext, new collection names or negotiation cannot override those existing format bounds; future representation changes require a separately published version decision consistent with this rule (OQ-05).

## 1. Scope

PallaSync is an accountless, end-to-end encrypted synchronization protocol for structured application data across one user's devices. It was first introduced for Palleria. It provides:

- Account-free onboarding. A 24-word BIP39 mnemonic and optional passphrase are the sole source of root authority; required Device-based Shamir Recovery support reconstructs this input when a set has been explicitly provisioned.
- End-to-end confidentiality with AEAD encryption (XChaCha20-Poly1305) under **rotating epoch keys**.
- Per-record integrity and authenticity through Ed25519 device signatures.
- Per-request authorization through short-lived, audience-bound, replay-protected Capability Tokens.
- Deterministic convergence for every collection (§15).
- Bounded metadata exposure through encrypted collection and operation fields and size bucketing (§14).
- Safe device lifecycle: enrollment approval, revocation with key rotation, auditable self-healing.
- Data ownership: standard export, relay migration, defined deletion guarantees.

A PallaSync server ("relay") is a blind relay and ciphertext store. It holds no decryption keys and cannot interpret payloads. The relay does the following:

- Validates wire structure.
- Verifies capability tokens and the signatures on records, devices, epochs and compactions.
- Enforces epoch linearity, membership, size limits and rate limits.
- Assigns `relay_seq`.
- Persists records durably.

Out of scope: peer-to-peer synchronization transport, federation between relays (§17.6), and application UI. Local enrollment control-object transfer in §18.1 and protected recovery transfer in §18.6 do not add peer-to-peer application-data synchronization. Every conformant client implements the recovery UI requirements in §18.9 and the explicit policy-consent/source-selection guards in §11.6–§11.7.

## 2. Threat Model & Security Properties

### 2.1 Invariants

1. **I-1 Accountless.** The protocol MUST NOT require a user account, email, phone number, or any identifier that the server can link to a natural person.
2. **I-2 Mnemonic as the sole root.** All root authority (admin key, recovery key-encryption key, chain identity) MUST be derivable from the 24-word BIP39 mnemonic plus an optional BIP39 passphrase, and from nothing else. Direct mnemonic entry is the default recovery method. Device-based Shamir Recovery (§5.6) reconstructs those same inputs; it introduces no independent root key. Without the mnemonic/passphrase or a usable provisioned threshold of shares, root authority cannot be recovered; an enrolled device alone has only its existing device/epoch authority.
3. **I-3 Blind relay.** The relay MUST NOT receive any key that can decrypt record payloads, device metadata, or epoch secrets; recovery shares, RMS, RSWKs and local recovery packages are also prohibited.
4. **I-4 Cryptographic model.** Confidentiality uses AEAD. Authenticity uses Ed25519. Authorization uses Capability Tokens.

### 2.2 Adversaries

| Adversary | Capabilities assumed | Protected properties |
|---|---|---|
| A1 Network attacker | Observes and modifies traffic outside TLS. Observes TLS metadata (timing, sizes, IP). | Confidentiality, integrity, replay resistance. |
| A2 Honest-but-curious relay | Reads all stored data and all observable metadata (§14.5). Follows the protocol. | Confidentiality of payloads, collection names, operations, entity IDs, device names. |
| A3 Malicious relay | Can drop, delay, reorder, withhold, replay, or fork data. Can roll back state. Can serve different views to different devices. | Forged signatures are detected; conflicting forks/rollback are detected against persisted or independent checkpoints (§13.7). Withholding is partly detected (§17.3). **Availability is not protected.** |
| A4 Stolen or compromised device (not holding the mnemonic) | Holds the device private keys and the epoch secrets it has received. | After revocation and rotation: no access to new epochs. Server access is refused. Past data follows the retention profile (§13.5). |
| A5 Revoked device that kept copies | Retains every ciphertext and key it ever obtained. | Nothing it already obtained can be taken back. This limit is fundamental and is stated in §20.2. |
| A6 Mnemonic compromise | Holds root recovery inputs, including the optional passphrase when used. | **None.** The mnemonic is root. The only remedy is migrating to a new chain with a new mnemonic (§13.8). |
| A7 Compromised Recovery Share Holder | Can extract its one share, wrapped-key credentials, blob and public set metadata; can retain copies indefinitely. A reader/collector can expose every secret handled during an active ceremony. | Fewer than threshold distinct RMS shares do not reconstruct RMS. Threshold shares plus the blob compromise root inputs. Regeneration cannot revoke retained old threshold material (§20.4). |

Recovery endpoints, their displays and their local authentication are trusted during a ceremony. Device IDs are not proof of independent physical storage. Implementations MUST require explicit user selection of independent holder security domains; a cloned device/medium does not count twice. A single compromised reader that also holds another share may see two distinct shares transiently; users MUST be warned before selecting it. Availability of holders, offline unlock credentials and application ciphertext is not guaranteed.

### 2.3 Security Properties

1. **P-1 Payload confidentiality** against A1 and A2/A3, for every epoch the adversary does not hold.
2. **P-2 Record authenticity.** Every applied operation has a valid enrolled-device signature. Pre-revocation acceptance eligibility is enforced by an honest relay and verified against authenticated historical evidence; an unobserved backdated acceptance claimed by a malicious relay cannot be proved from the signature alone (§18.4).
3. **P-3 Forward protection after revocation.** Records written after a rotation are encrypted under a secret that revoked devices never receive.
4. **P-4 Metadata minimization.** The server can observe only the fields listed in §14.5.
5. **P-5 Replay resistance.** Capability tokens are single-use within their lifetime and bound to one audience, method, path, query, and body.
6. **P-6 Convergence.** Two clients that have applied the same log prefix, or the same snapshot plus log suffix, have identical materialized state (§15.1).
7. **P-7 Detectability.** Invalid signatures and AAD mismatches are detected. Epoch forks and rollbacks are detected when they contradict a persisted checkpoint or an independently authenticated view (§13.7). An isolated first-time client cannot detect a consistently withheld view. Record withholding is detected on a best-effort basis (§17.3). Relay signatures prove statements made by the pinned relay key, not delivery completeness, physical durability or erasure (§17.9).
8. **P-8 Root-input recovery.** A correctly provisioned usable threshold of independent Recovery Share Holders can reconstruct the original mnemonic/passphrase without the relay; access to application data still requires retained ciphertext and envelopes (§20.4).

## 3. Wire & Serialization Conventions

### 3.1 JSON Profile

All requests, responses, signed objects and decrypted plaintexts MUST follow these rules. A receiver MUST reject input that breaks any rule. Servers respond with `400 INVALID_JSON` or `400 INVALID_FIELD`. Clients quarantine the input with `C_SCHEMA_VIOLATION` (§19.3).

| Rule | Requirement |
|---|---|
| J-1 Encoding | UTF-8 without BOM. Invalid UTF-8 sequences are rejected. |
| J-2 Strings | No lone surrogates (`\ud800`–`\udfff` unpaired). No U+0000 in any identifier field. |
| J-3 Duplicate keys | Objects with duplicate member names are rejected. A last-wins parser is not acceptable. |
| J-4 Numbers | Only integers matching `0\|[1-9][0-9]*`, in the range `0 … 9007199254740991` (2^53−1). The following are rejected: fractions, exponents, a leading `-`, `-0`, leading zeros, and values outside the range. **Floating point is forbidden everywhere.** |
| J-5 Depth | Maximum nesting depth is 32. |
| J-6 Unknown members | Unknown members are rejected, except inside an `ext` object (§3.6). |
| J-7 Null | `null` is allowed only where a field is typed as nullable. An absent field and a `null` field are different. Each field definition says which form is allowed. |

### 3.2 Canonicalization (JCS)

- Every signed structure and every AAD MUST be serialized with **JCS (RFC 8785)** before it is hashed, signed, or used as AAD.
- Signature verification MUST re-canonicalize the **parsed** object. Received bytes MUST NOT be verified as they arrive. Since J-4 forbids non-integer numbers, JCS number serialization reduces to decimal integer printing. This removes the most common source of differences between JCS implementations.
- JCS sorts object members by their **UTF-16 code unit** sequence, not by Unicode code point and not by UTF-8 bytes. Vector `JCS-02` (Appendix C.1) MUST pass.
- JCS escapes only `"`, `\`, and U+0000–U+001F. It uses the short forms `\b \f \n \r \t` and `\u00XX` (lowercase hex) otherwise. `/` and non-ASCII characters are emitted literally. Vectors `JCS-03` and `JCS-04` MUST pass.
- Relays MUST store and return every client-signed object so that it parses to the same JSON value. Relays MAY re-serialize whitespace. Relays MUST NOT change string contents, member names, or integer values.

**Validation procedure.** Every implementation MUST include a JCS self-test in its test suite. The test MUST run:
1. Parse each Appendix C.1 input.
2. Serialize it with JCS.
3. Compare the result byte-for-byte with the expected output.
4. Compare its SHA-256 with the expected hash.
5. Feed each Appendix C.1 negative input (floats, duplicate keys, lone surrogate, `-0`, `1e3`, `01`) and confirm that it is rejected.

### 3.3 Unicode Normalization

- Every field defined as an *identifier string* MUST be in **Unicode Normalization Form C (NFC)** when written. This covers `entity_id`, `body.tag`, `body.query`, `body.value`, `collection`, settings keys, and order keys.
- Writers MUST normalize user input to NFC before constructing an operation.
- Receivers MUST check NFC. An operation with a non-NFC identifier is quarantined with `C_SCHEMA_VIOLATION`. Receivers MUST NOT normalize it silently, because that would change signed content and break convergence.
- Free-text display fields (`title`, `artistName`, device `name`) are not identifiers. They MUST still be valid per J-2. Writers SHOULD normalize them to NFC. If they do not, the same title may display differently on different platforms; convergence is not affected.
- Case is significant in identifiers. `"Miku"` and `"miku"` are different entities. Case folding, if desired, is an application choice made **before** the operation is written.

### 3.4 Binary, Identifier and Time Encodings

| Type | Encoding | Validation |
|---|---|---|
| `b64u(n)` | Base64URL, RFC 4648 §5, no padding | Exact decoded length `n` where specified. Alphabet `[A-Za-z0-9_-]` only. Non-canonical trailing bits MUST be rejected. |
| `uuid4` | Lowercase hyphenated UUID version 4 | Regex `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Generated from a CSPRNG. |
| `chain_id` | `b64u(32)`, 43 characters | §5.1 |
| `ms` | Unix epoch milliseconds, integer | `0 … 2^53−1` |
| `seq` | Relay sequence number, integer ≥ 1 | Strictly increasing per `(chain_id, log_id)`, never reused in that incarnation (§17.2) |

**Clock usage.** Client wall clocks are untrusted. They MUST NOT be used for ordering or conflict resolution. Ordering uses Lamport stamps (§15) and `relay_seq`. Client timestamps (`created_at_ms`, `approved_at_ms`, `issued_at_ms`) are used only for display, audit, and token freshness (§6.3). Time-based retention (grace periods, scheduled rotation) uses the relay-assigned `committed_at_ms` (§7.6).

### 3.5 Size Notation

`KiB` = 1,024 bytes. `MiB` = 1,048,576 bytes. `GiB` = 1,073,741,824 bytes.

### 3.6 Extension Member

Signed objects MAY contain `"ext": { … }`, an object whose members are named `<reverse-dns>.<name>` (for example `"com.example.flag"`).
- `ext` content is covered by the signature, because it is part of the JCS input.
- Receivers MUST ignore `ext` members they do not understand.
- `ext` MUST NOT change the semantics of any field defined in this document.
- The maximum encoded size of `ext` is 1 KiB, measured as `len(UTF8(JCS(ext)))`.
- Extension names MUST have at least three dot-separated ASCII labels. Each namespace label matches `[a-z][a-z0-9-]{0,62}` with no trailing hyphen; the final name matches `[a-z][a-z0-9_]{0,63}`. Full name length is at most 255 bytes. Receivers validate syntax only, not live DNS ownership. This grammar gives the reverse-DNS naming convention a deterministic wire check.

## 4. Cryptographic Algorithms & Context Strings

| Purpose | Primitive | Specification | Notes |
|---|---|---|---|
| Recovery mnemonic | BIP39 | 256-bit entropy, English wordlist | 24 words, checksum verified on entry |
| Mnemonic seed | BIP39 PBKDF2 | HMAC-SHA512, 2,048 iterations, salt `"mnemonic" ‖ passphrase`, NFKD | Passphrase defaults to `""` |
| Key derivation | HKDF-SHA256 | RFC 5869 | Domain-separated `info` strings |
| Payload and metadata encryption | XChaCha20-Poly1305 | draft-irtf-cfrg-xchacha-03; 256-bit key, 192-bit random nonce, 128-bit tag | CSPRNG nonce for every encryption |
| Epoch secret delivery to devices | HPKE | RFC 9180, mode_base, KEM `0x0020` DHKEM(X25519, HKDF-SHA256), KDF `0x0001` HKDF-SHA256, AEAD `0x0003` ChaCha20Poly1305 | Single-shot |
| Device signatures, admin signatures | Ed25519 | RFC 8032 (pure Ed25519, no prehash) | Verification MUST reject non-canonical `S` (`S ≥ L`) and small-order public keys |
| Collection tag | HMAC-SHA256 | RFC 2104 | Truncated to 16 bytes |
| Hash | SHA-256 | FIPS 180-4 | |
| Canonical serialization | JCS | RFC 8785 | §3.2 |
| Legacy decryption (migration only) | ChaCha20-Poly1305 | RFC 8439, 96-bit deterministic nonce | §9 |

**Strict public-key/signature validation profile.** For all v3 Ed25519 uses, the encoded public point A and signature point R MUST be canonical, non-identity points in the prime-order subgroup; S MUST satisfy `0 ≤ S < L`. Verification MUST check the uncofactored equation `[S]B = R + [k]A` with the RFC 8032 pure-Ed25519 challenge k, and MUST NOT accept a signature solely because a cofactor-multiplied equation holds. Use vetted-library point/subgroup and signature validation. Writers MUST check the same profile on their generated keys/signatures. Only independently random device/HPKE keys may be regenerated; root derivation MUST NOT change. A degenerate signature is retried by varying the object's fresh ID/nonce or adding a signed random `org.palleria.signature_nonce` extension (b64u(16), ignored for application semantics) before first publication. Already committed objects are immutable. This validation subset prevents library-dependent acceptance of malformed/torsion signatures; it changes no algorithm, key length, context or valid ordinary vector.

X25519 public keys and HPKE `enc` MUST encode a little-endian u coordinate less than `2^255−19` with the high bit clear. Receivers MUST reject noncanonical coordinates before DH/HPKE rather than mask/reduce them differently across libraries, and MUST reject an all-zero DH output. Compliant generated X25519 public keys already satisfy this encoding profile. Private-key clamping remains the vetted primitive's operation.

## 5. Key Derivation Hierarchy

### 5.1 Root Derivation & Chain ID

```
root_seed       = BIP39.to_seed(NFKD(mnemonic), NFKD(passphrase))             // 64 bytes
chain_salt      = SHA-256("PALLASYNC-CHAIN-SALT-v3\0" || root_seed)            // 32 bytes
chain_id_digest = SHA-256("PALLASYNC-CHAIN-ID-v3\0" || chain_salt || root_seed) // 32 bytes
chain_id        = b64u(chain_id_digest)                                        // 43 chars
```

- `chain_salt` is deterministic. 2.1 allowed a random salt, which made mnemonic-only recovery impossible. That option is removed. Requirement I-2 does not allow any parameter other than the mnemonic and passphrase.
- The mnemonic MUST be validated (wordlist membership and checksum) before derivation. Invalid input MUST be rejected with a user-facing error. Implementations MUST NOT attempt to "auto-correct" it.
- A non-empty passphrase produces a different chain. The UI MUST state this when a passphrase is entered.

### 5.2 Root-Level Keys (mnemonic holders only)

```
prk           = HKDF-Extract(salt = chain_salt, IKM = root_seed)
admin_seed    = HKDF-Expand(prk, "PALLASYNC-v3\0admin-ed25519\0", 32)
admin_key     = Ed25519.SigningKey(admin_seed)
admin_public_key = admin_key.public                                      // published in ChainParameters
recovery_kek  = HKDF-Expand(prk, "PALLASYNC-v3\0recovery-kek\0", 32)     // wraps epoch secrets for recovery
```

These keys exist only while the user is performing a mnemonic-authorized operation (§5.5).

### 5.3 Epoch Secrets and Epoch-Derived Keys

Each epoch `n` (`uint32`, starting at 0) has one secret:

```
epoch_secret_n = CSPRNG(32)          // generated by the author of EpochRecord n
```

`epoch_secret_n` is never derived from the mnemonic. It is delivered only through `EpochKeyEnvelope`s (§7.7). Those envelopes are:
- HPKE-encrypted to each member device's `device_kex_public_key`, and
- XChaCha20-Poly1305-encrypted under `recovery_kek` (one recovery envelope per epoch).

Derived keys:

```
epoch_prk          = HKDF-Extract(salt = "PALLASYNC-v3\0epoch\0" || chain_id_digest || uint32_be(n),
                                  IKM  = epoch_secret_n)
record_key_n       = HKDF-Expand(epoch_prk, "PALLASYNC-v3\0record\0", 32)
device_meta_key_n  = HKDF-Expand(epoch_prk, "PALLASYNC-v3\0device-meta\0", 32)
collection_tag_key_n = HKDF-Expand(epoch_prk, "PALLASYNC-v3\0collection-tag\0", 32)
epoch_commitment_n = HKDF-Expand(epoch_prk, "PALLASYNC-v3\0epoch-commitment\0", 32)  // public
```

- `epoch_commitment_n` is published in `EpochRecord n`. A device that unwraps an envelope MUST derive `epoch_commitment_n` and compare it with the published value in constant time. On mismatch, the device MUST reject the envelope with `C_COMMITMENT_MISMATCH`. This stops a malicious sender or relay from giving different members different keys for the same epoch.
- Epoch secrets are independent. Knowing `epoch_secret_n` reveals nothing about `epoch_secret_{n+1}`. There is no hash ratchet. Holding a newer epoch secret does not grant access to older epochs; older secrets must be delivered explicitly (§13.5).

### 5.4 Device Keys and Mandatory Secure Storage

Each device generates, from a CSPRNG and on the device:
- `device_signing_key`: Ed25519, signs that device's records, DeviceRecord, tokens, envelopes.
- `device_kex_key`: X25519, receives epoch envelopes.

Device keys MUST NOT be derived from the mnemonic. The 2.1 option of using "the derived signing key" is removed, because a shared derived key makes it impossible to revoke one device.

**Storage requirement (MUST).** The following MUST be stored using one of the protections below. They MUST NOT be stored in plaintext files, plain preferences, logs, crash reports, or backups that leave the device:
- `device_signing_key`
- `device_kex_key`
- every retained `epoch_secret_n`
- every `epoch_prk` or derived key that is cached
- every Recovery Share Wrapping Key (RSWK), when a holder is provisioned (§5.6)

| Platform | Accepted protection | `key_protection` value |
|---|---|---|
| Android | Keys wrapped by an Android Keystore key (StrongBox when available). Wrapped blobs MAY live in app storage. Backups MUST exclude them (`android:allowBackup` rules or `dataExtractionRules`). | `os-keystore` or `hardware` (StrongBox/TEE attested) |
| iOS / iPadOS / macOS | Keychain with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` or stricter. Secure Enclave wrapping when available. | `os-keystore` or `hardware` |
| Windows | DPAPI (user scope) or CNG with a TPM-backed key. | `os-keystore` or `hardware` |
| Linux desktop | Secret Service API (libsecret / KWallet), unlocked per session. | `os-keystore` |
| Browser extension / web | WebCrypto `CryptoKey` objects created with `extractable: false` and stored in IndexedDB. If a primitive is not available as a non-extractable key, the raw key MUST be wrapped by a non-extractable AES-GCM key. | `webcrypto-nonextractable` |
| Any platform without the above | Keys encrypted with XChaCha20-Poly1305 under a key derived from a user-chosen passphrase via Argon2id (m = 65,536 KiB, t = 3, p = 1, 16-byte random salt). The passphrase MUST be requested at every process start. | `passphrase-wrapped` |

If none of the above is available, the implementation MUST refuse to enroll the device. Each device declares its protection class in its encrypted device metadata (§7.4). Other devices MUST display it, so the user can judge whether to trust a weakly protected device.

### 5.5 Material that MUST NOT be Persisted

A device MUST NOT persist any of the following to non-volatile storage:
- the mnemonic
- the passphrase
- `root_seed`, `chain_salt`, `prk`
- `admin_seed` / `admin_key`
- `recovery_kek`

They MAY be held in memory only while a mnemonic-authorized operation runs (genesis, mnemonic enrollment, emergency revocation, admin-signed requests, explicit recovery setup/ceremony). When that operation completes, fails or is cancelled, they MUST be zeroized. RMS, plaintext Recovery Secret, polynomial coefficients and unwrapped recovery shares MUST also remain transient and be zeroized. The sole recovery-storage exception is one locally wrapped share with its encrypted RecoverySecretBlob and signed public set/status metadata (§7.11); persisting a full Recovery Secret or RMS under a device key is still prohibited. A holder retains its encrypted package, not the ceremony's temporary copies.

> [!WARNING]
> This rule is what makes revocation meaningful. A device that complied with §5.5 and is later stolen holds its device keys, received epoch secrets and, if opted in, at most one protected recovery share. One share does not confer root authority; threshold collusion or compromise during a ceremony does. Rotation therefore locks it out of new data (§13). A device that did **not** comply, or that was malicious while the user typed the mnemonic, effectively holds root authority. That case is handled as mnemonic compromise (§13.8).

### 5.6 Device-based Shamir Recovery

Every conformant PallaSync 3.0 client MUST implement set creation/distribution, protected holding/offline export, explicit threshold recovery and lifecycle/error/UI handling in §7.11, §11.4 and §18.6–§18.9. Shamir support is not OPTIONAL and a client without it MUST NOT claim v3.0 client conformance. A newly configured chain starts `not_provisioned`; set creation/enabling requires explicit user consent and a mnemonic-holder session. App upgrades preserve existing valid set/status state and never reset, regenerate or provision a set automatically. Mandatory implementation does not authorize automatic setup, share allocation, release or recovery. Direct mnemonic entry remains the default root-input method. Relay-only services implement their relay obligations and never become share holders.

**Terms.** Recovery Secret is the canonical recovery input `{mnemonic:string,passphrase:string}`. Recovery Master Secret (RMS) is an independent CSPRNG 32-byte secret encrypting that input. A Recovery Share is one Shamir piece of RMS, thereby indirectly protecting the Recovery Secret. A Recovery Share Set shares `recovery_set_id`, `threshold`, `total_shares`, `created_at_ms` and `recovery_secret_fingerprint`. A Recovery Share Holder is a device or offline medium retaining exactly one protected piece. Recovery Ceremony is the explicit collection, verification, reconstruction and authorized-operation lifecycle. RSWK means the independent 32-byte Recovery Share Wrapping Key generated by each holder. None is derived from admin, device, epoch, recovery_kek or another holder's keys.

The Recovery Secret mnemonic MUST be a checksum-valid 24-word BIP39 English phrase, lowercase words separated by exactly one ASCII space, with no leading/trailing space. `passphrase` is always present, including empty string, and is NFKD as required by BIP39. Writers normalize passphrase input before creating the blob; receivers MUST reject a blob that is not already canonical. Passphrase correctness is checked by deriving the expected chain/admin identity; BIP39 has no separate passphrase checksum. Fingerprint is b64u(SHA-256(ASCII(`PALLASYNC-RECOVERY-SECRET-FP-v3\0`) || JCS(Recovery Secret))). This value is local/encrypted-audit metadata, not a public relay index: it permits candidate-input confirmation if exposed.

The fixed local profile is `shamir-gf256-aes/1`: bytewise GF(256), polynomial basis, reduction polynomial x^8+x^4+x^3+x+1 (`0x11b`), XOR addition, ordinary field multiplication/reduction and division by multiplicative inverse. For each of RMS's 32 bytes independently choose t−1 uniform CSPRNG coefficient bytes (zero included); f_j(x)=RMS[j] XOR sum(a_j,k * x^k). Share i contains the 32 bytes f_j(i), with x=i in 1…n. Require `2 <= threshold < total_shares <= 255`; default t=2,n=3. 2-of-4, 3-of-4 and 3-of-5 use the same profile. Reconstruct at zero using Lagrange interpolation in this field; never use integer/real arithmetic. For the lowest t distinct valid indexes, RMS[j] = XOR_i(y_i[j] * product_(k!=i)(x_k / (x_k XOR x_i))). Extra supplied shares MUST agree with the interpolated polynomial; reject inconsistent input rather than search subsets or silently correct it.

The threshold construction follows [Shamir's original scheme](https://dspace.mit.edu/entities/publication/91c51bfc-5678-409c-80c5-44ce8fcdbadf); the field arithmetic uses [FIPS 197's GF(256) representation](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197-upd1.pdf). This local encoding is not SLIP-0039 and MUST NOT be replaced by a library's incompatible reserved-index, word-list or checksum format. With fewer than t raw pieces the sharing component hides RMS; the complete system additionally relies on AEAD/hash security and trusted endpoints.

Encrypt the canonical RecoverySecretBlob plaintext (§7.11.1), framed/padded as §14.3, using RMS directly as the XChaCha20-Poly1305 key and a random 24-byte `blob_nonce`. Encrypt each raw 32-byte share under its holder's RSWK and random 24-byte `share_wrap_nonce` with the exact share AAD (§7.11.2). Keys/nonces and signed bindings are independent of record/epoch encryption. RSWK MUST use a §5.4 protection class, backup exclusion and per-release biometric/PIN authentication where available; otherwise require the explicit protection-class unlock and user consent for every release. RSWK MUST NOT leave its holder or be sent to the setup dealer. Offline portability uses §7.11.4's separately credential-wrapped RSWK.

Set creation, replacement and disablement require a mnemonic-holder session, entered directly or obtained after a verified explicit ceremony. Regeneration MUST create a fresh RMS, fresh independent polynomials, new set/share IDs, fresh RSWKs and blob/nonces; no old RMS/blob/share is reused. Replacing RMS requires replacing all shares, not merely swapping the blob. Changing a BIP39 passphrase changes root_seed and chain_id (§5.1): perform new-chain migration and provision a new set there. These operations never change the existing root derivation hierarchy.

### 6.2 Query Canonicalization

1. Split the raw query on `&`. Split each pair on the first `=`; a missing `=` means an empty value.
2. Percent-decode names and values. Then re-encode them, leaving only the RFC 3986 unreserved characters `A–Z a–z 0–9 - . _ ~` unescaped and using uppercase hex.
3. Sort the pairs by name, then by value, comparing bytes.
4. Join as `name=value` with `&`. An empty query gives `""`.

Example: `?limit=200&after_seq=0` canonicalizes to `after_seq=0&limit=200`.

### 6.3 Freshness, Clock Skew and Replay

The relay MUST reject a token unless all of the following hold. `now` is the relay clock in milliseconds and the skew `σ = 60000`.

1. `issued_at_ms ≤ now + σ`. Otherwise the relay returns `401 TOKEN_NOT_YET_VALID`.
2. `now ≤ expires_at_ms + σ`. Otherwise the relay returns `401 TOKEN_EXPIRED`.
3. `expires_at_ms − issued_at_ms ≤ 300000` (server acceptance ceiling, not the client authoring TTL). Otherwise the relay returns `401 TOKEN_TTL_TOO_LONG`.
4. The tuple `(chain_id, signer_kind, device_id, nonce)` has not been seen. The relay MUST remember every accepted tuple until `expires_at_ms + σ`. A repeat gets `401 TOKEN_REPLAYED`. The replay cache MUST survive process restarts (it is persisted or replicated). Alternatively, after a restart the relay MUST reject every token whose `issued_at_ms` is earlier than the restart time plus σ.
5. The signature is valid, and `aud`, `method`, `path`, `query`, and `body_sha256` match. Otherwise the relay returns `401 TOKEN_SIGNATURE_INVALID` or `401 TOKEN_BINDING_MISMATCH`.

The replay check and nonce reservation MUST be atomic after authentication and before executing the request. A token is consumed even if the authenticated operation subsequently fails. `issued_at_ms < expires_at_ms` is independently required. Query percent escapes MUST be valid; `+` is a literal plus, not a space. Endpoint query names MUST be unique and drawn from the endpoint's declared set. HTTP request content encoding MUST be identity; the body digest is computed before parsing. The mnemonic, keys and tokens MUST NOT be included in URLs or relay logs.

A relay using the restart replay-cache alternative returns TOKEN_NOT_YET_VALID for tokens below its restart barrier and context retry_after_ms until the barrier ends. Clients MUST honor that wait; applying the Date-header clock offset alone cannot bypass the restart barrier. This temporary barrier never triggers enrollment or key erasure.

The 300-second ceiling is intentional defense/acceptance tolerance; conformant clients still author exactly 120 seconds below. No relay may infer permission for a client to author 300-second tokens. At the restart fallback, record a trusted restart time R and barrier B=R+60000 before processing tokens; never move B backward. All replicas accepting the same nonce namespace MUST share durable replay state or coordinated barriers so switching replicas cannot bypass protection. If safe clock/barrier coordination is unavailable, fail closed until established. Repeated restarts establish a new barrier and can extend unavailability.

For an honest client issuing at the corrected relay time, new tokens reach B approximately 60 seconds after R; a client clock behind by the permitted 60 seconds may need approximately 120 seconds. The exact predicate is issued_at_ms >= B, not an unconditional wall-clock sleep: permitted future timestamps can satisfy it earlier. TOKEN_NOT_YET_VALID includes context.retry_after_ms and Retry-After based on the failing timestamp/barrier; retry only after the indicated delay with a freshly issued token and corrected offset. These durations are not availability guarantees under clock faults/repeated failures. Operators using this fallback MUST disclose the restart-induced delay, coordination and recovery process in privacy.md and privacy.json, monitor recurring barriers, and provide a durable/replicated cache for normal uninterrupted service. No re-enrollment or key deletion is a recovery step.

Clients MUST create a new token for each request, including retries. Clients MUST use `expires_at_ms = issued_at_ms + 120000` (2 minutes). If a client receives `TOKEN_EXPIRED` or `TOKEN_NOT_YET_VALID` twice in a row, it MUST calculate its offset from the relay's `Date` header (or from `server_time_ms`) and apply that offset when issuing tokens.

### 6.4 Admin Tokens

`signer_kind = "admin"` tokens are signed with `admin_key`. Creating one requires the mnemonic (§5.5). Admin tokens are REQUIRED for:
- `POST /chains` (genesis)
- recovery-envelope retrieval
- mnemonic enrollment
- emergency rotations
- `DELETE /chains/:chain_id` (unless the policy allows otherwise)
- `PUT /chains/:chain_id/parameters` (re-seed, §17.5)

Admin tokens MAY be used for any read endpoint.

## 7. Wire Data Models

In the tables below, **R** means REQUIRED, **O** means OPTIONAL (absent when unused), and **N** means REQUIRED but nullable. A dash in the default column means that there is no default. All integer bounds also obey §3.1. `uint32` means `0 … 4294967295`; `counter` means `1 … 9007199254740991`. All signed objects have a REQUIRED `signature: b64u(64)` and OPTIONAL `ext: object` as in §3.6. These two members are implicit in the signed-object tables below. Defaults describe values a writer MUST explicitly put into required fields; verification MUST NOT insert defaults. Arrays retain their order under JCS.

`object_hash(X) = b64u(SHA-256(JCS(X)))`, including X's signature and excluding response wrappers. Unless expressly specified otherwise, hashes below use this function. Identifiers MUST be NFC. Byte limits on strings mean their UTF-8 length. A reused identifier with different signed content is an equivocation, not an update. Request examples containing `<…>` are structural illustrations, not cryptographic vectors.

Encrypt with `record_key_n`, `payload_nonce`, this AAD, and the framing in §14.3.

#### 7.11.3 RecoveryPackage and Storage

RecoveryPackage is `{type:"PALLASYNC-RECOVERY-PACKAGE-v3",version,manifest:RecoveryShareSetManifest,status_chain:RecoverySetStatus[],record:RecoveryShareRecord,blob:RecoverySecretBlob,offline_key_envelope:OfflineShareKeyEnvelope|null}`. Each physical device MUST persist at most one share package across all sets/chains/apps and device identities participating in this feature. If a platform cannot enforce protected storage and backup exclusion, disable share holding with C_RECOVERY_STORAGE_UNSAFE. RecoverySessionDescriptor is `{type:"PALLASYNC-RECOVERY-SESSION-v3",version,ceremony_id:uuid4,session_id:uuid4,endpoint_id:uuid4,side:"initiator"|"responder",role:"dealer"|"holder"|"reader"|"collector",purpose:"create"|"rotate"|"recover"|"disable",chain_id,generation,recovery_set_id,set_manifest_hash:b64u(32),session_nonce:b64u(32),session_signing_public_key:b64u(32),session_kex_public_key:b64u(32),ttl_ms:300000,signature:b64u(64)}`. It is self-signed by its session Ed25519 key; that is possession evidence, not enrolled-device or root authority. Each process enforces five-minute monotonic expiry from establishing the pair and never resumes a secret session after restart. A new pair requires fresh keys/IDs and user consent. The signed descriptors are physically/locally exchanged over QR, local Wi-Fi, USB or OS proximity sharing; they and recovery transfers MUST NOT be relayed through the PallaSync relay, a hosted mailbox or remote telemetry.

Compute DH with the local session X25519 private key and peer public key. SAS is the first six bytes of SHA-256(ASCII(`PALLASYNC-RECOVERY-SAS-v3\0`) || DH || JCS({initiator:complete_signed_descriptor,responder:complete_signed_descriptor})), displayed as 12 lowercase hex digits in three groups of four. BOTH endpoints MUST display/explicitly confirm equal SAS and recipient/purpose before any share-bearing payload is emitted or accepted. Mismatch, cancellation, unconfirmed screens or expiry abort without transfer. Enrollment's existing SAS context/keys MUST NOT be reused. Long-term device attestations MAY additionally authenticate the path but cannot omit live SAS.

RecoveryTransfer is `{type:"PALLASYNC-RECOVERY-TRANSFER-v3",version,transfer_id:uuid4,session_id:uuid4,sender_descriptor_hash:b64u(32),recipient_descriptor_hash:b64u(32),message_seq:integer,message_kind:enum,enc:b64u(32),ciphertext:b64u(variable),signature:b64u(64)}` signed by the sending session key. `message_seq` starts at 1 per sender and increments exactly one, no wrap. `message_kind` is distribute_share, wrap_proposal, signed_share, persisted, collect_share or result. Header is the object excluding enc,ciphertext,signature. HPKE uses §4's base suite, recipient session X25519 key, info ASCII(`PALLASYNC-RECOVERY-TRANSFER-HPKE-v3\0`) || JCS(Header), aad JCS(Header), fresh encapsulation for each message. Plaintext is UTF-8 JCS of exactly the corresponding payload below; transfer and decrypted plaintext are bounded to 4,194,304 bytes. This local control transfer has no record padding or log receipt. Never reuse an EpochKeyEnvelope or epoch secret as its container/key.

| message_kind | Exact decrypted payload |
|---|---|
| distribute_share | `{manifest,blob,share_index:integer,raw_share:b64u(32)}`; dealer→selected holder/issuer. |
| wrap_proposal | `{record:RecoveryShareRecord without signature}`; holder→dealer for admin signing; no RSWK. |
| signed_share | `{record:RecoveryShareRecord}`; dealer→holder, validates its unchanged proposal. |
| persisted | `{recovery_share_id:uuid4,record_hash:b64u(32),verified:boolean}`; holder→dealer after persistence/readback. |

Session role/purpose, stage, signature, descriptor hashes, sequence and exact set binding are verified before decrypting or consuming a payload. result.code is null or a literal code defined in §19, at most 64 ASCII bytes; arbitrary diagnostic text or secret values are prohibited. Exact repeated transfer bytes return the cached public acknowledgement without counting/processing a share twice; same sequence/ID with different bytes is C_RECOVERY_SHARE_INVALID. Out-of-order packets are not applied; sender retries the exact missing packet. This does not change Capability Tokens: session keys never authorize relay/admin operations.

### 7.12 Relay Attestations

These attestations add relay accountability, not E2EE/root authority. All listed fields are REQUIRED, no defaults/unknown keys; strict §3 and §4 apply. `relay_key_id` is b64u(SHA-256(decoded relay_public_key)); the independent random relay Ed25519 key is pinned for the user-selected origin (§17.9). Relay structures use `relay_signature` covering every other member under §4.1; device witnesses/checkpoints use their own `signature` and certified device key. New attestations MUST NOT be inserted into LogEntry, SyncRecord, RecordAAD or an existing client-signed object, so §17.3's H_i calculation is unchanged. Key IDs are identifiers, not secrets.

#### 7.12.1 UploadReceipt

`{type:"PALLASYNC-UPLOAD-RECEIPT-v3",version:"3.0",receipt_id:uuid4,chain_id,log_id:uuid4,relay_key_id:b64u(32),relay_seq:seq|null,object_hash:b64u(32),entry_hash:b64u(32)|null,previous_head_hash:b64u(32),resulting_head_hash:b64u(32),received_at_ms:ms,transparency_id:uuid4,transparency_index:seq,transparency_hash:b64u(32),relay_signature:b64u(64)}`.

`object_hash=SHA-256(JCS(LogEntry.object))`, including its client signature; `entry_hash=SHA-256(JCS(LogEntry))`. `previous_head_hash=H_(seq−1)`, `resulting_head_hash=H_seq` exactly §17.3, even if other transaction entries follow it. received_at_ms matches the immutable LogEntry. Transparency reference names the exact accept entry for that object/seq. For a snapshot-part-store acceptance, relay_seq and entry_hash are null, object_hash hashes its exact signed SyncRecord and previous_head_hash=resulting_head_hash is the unchanged current H; the accept transparency entry also has relay_seq=null. This receipt proves a storage commitment, not data-log inclusion or snapshot semantic completeness. Receipt is committed with the object, any log update and transparency entry before acceptance is returned. Exact retries return the original immutable receipt, not new IDs/times. Signature authenticates the relay's commitment; verify its hash recurrence and eventual inclusion against pinned heads. It cannot prove physical durability or pre-revocation acceptance time for a previously unseen view signed by a malicious relay.

#### 7.12.2 RelayTransparencyEntry and RelayTransparencyHead

RelayTransparencyEntry is `{type:"PALLASYNC-TRANSPARENCY-ENTRY-v3",version:"3.0",transparency_id:uuid4,entry_index:seq,chain_id,log_id:uuid4,relay_key_id:b64u(32),operation:"accept"|"reject"|"prune"|"delete"|"migrate",object_hash:b64u(32),relay_seq:seq|null,resulting_head_hash:b64u(32),previous_transparency_hash:b64u(32),timestamp:ms,code:string|null,relay_signature:b64u(64)}`. Index starts at 1, increases exactly one and never reuses a value in the same transparency_id. Timestamp is relay wall time, not trusted ordering/freshness. Accept has null code and hashes the accepted signed object; each new LogEntry has one accept entry with its non-null relay_seq. Snapshot-part-store acceptances have null relay_seq and the unchanged current resulting_head_hash, never a fabricated data-log position. Only these two acceptance classes are permitted. Reject has null relay_seq, its §19.2 code, and hashes the parsed candidate object. Prune/delete/migrate have null relay_seq/code and hash respectively JCS(`{compaction_id,through_seq}`), the ledger (including receipt_hash), or the exact published relay-notice value. For reject/prune/delete/migrate resulting_head_hash is the unchanged current H head; they do not fabricate data-log entries. Any accepted AdminOperation/control objects in their transaction receive their separate accept entries.

Let T0=SHA-256(ASCII(`PALLASYNC-TRANSPARENCY-v3\0`) || decoded chain_id || decoded transparency_id UUID bytes || decoded relay_key_id). For i>=1, Ti=SHA-256(ASCII(`PALLASYNC-TRANSPARENCY-LINK-v3\0`) || T_(i−1) || uint64_be(i) || SHA-256(JCS(complete signed RelayTransparencyEntry_i))). Its previous_transparency_hash is T_(i−1). Signed entries and hashes are immutable; own relay_signature is excluded only while signing, included while hashing. Transparency history survives ordinary data pruning and healthy backup/restore. Old heads/evidence are retained when an acknowledged suffix is lost; restoration uses a new transparency_id with explicit reconciliation, never silently resetting a pinned index. A new data log_id alone does not reset a healthy transparency chain.

RelayTransparencyHead is `{type:"PALLASYNC-TRANSPARENCY-HEAD-v3",version:"3.0",chain_id,log_id:uuid4,relay_key_id:b64u(32),transparency_id:uuid4,entry_index:integer,transparency_hash:b64u(32),head_seq:integer,head_hash:b64u(32),parameters_hash:b64u(32),epoch_hash:b64u(32),min_available_seq:seq,timestamp:ms,relay_signature:b64u(64)}`. Empty chain index=0/hash=T0; otherwise names a stored entry/hash. Data hashes/heads must describe the same atomic view. Timestamp does not prove that no later head exists. The head is published through authenticated chain access (§10.17); it is not a public enumeration of private chain IDs.

Authenticated, structurally parsed chain-object acceptances/rejections and every authorized prune/delete/published migration notice MUST be logged. Exact accepted retries append nothing; a rejected new attempt appends one reject per candidate object, never body/token/URL/IP/account data. Transport, unauthenticated, token-replay, rate-limited or malformed/unparseable requests are operational failures and cannot safely be assigned per-chain transparency entries; they MUST NOT reveal chain existence. That bounded scope is essential to prevent unauthenticated log flooding and privacy leakage. Quota accounting includes transparency storage; exhaustion blocks new mutations with §19.2's existing capacity errors rather than acknowledging unlogged writes. Reads/probes do not create transparency entries.

#### 7.12.3 DeleteReceipt and DeletionWitness

DeleteReceipt is `{type:"PALLASYNC-DELETE-RECEIPT-v3",version:"3.0",chain_id,deletion_id:uuid4,log_id:uuid4,relay_key_id:b64u(32),authorized_parameters_hash:b64u(32),authorized_epoch_hash:b64u(32),authorization_hash:b64u(32),requested_at_ms:ms,completed_at_ms:ms|null,assurance:"crypto-shred"|"backup-expiry",delete_after_ms:ms|null,ledger_receipt_hash:b64u(32),transparency_id:uuid4,transparency_index:seq,transparency_hash:b64u(32),relay_signature:b64u(64)}`. These fields exactly match the §17.7 ledger and the delete entry's reference. They are outside the ledger's receipt_hash, avoiding circular hashes. Completion updates produce a new signed receipt with unchanged authorization/deletion/transparency bindings and nondecreasing completion information; preserve earlier receipts as evidence. A completion attestation is an operator claim, not proof that a malicious relay has erased copies.

DeletionWitness is `{type:"PALLASYNC-DELETION-WITNESS-v3",version:"3.0",chain_id,deletion_id:uuid4,delete_receipt_hash:b64u(32),authorized_parameters_hash:b64u(32),authorized_epoch_hash:b64u(32),authorization_hash:b64u(32),witness_device_id:uuid4,created_at_ms:ms,signature:b64u(64)}` signed by a distinct active device at the authorized epoch. Witnesses attest observation/confirmation of the exact immutable receipt and its authorized deletion intent, not completed physical deletion. `delete_receipt_hash = b64u(SHA-256(JCS(complete DeleteReceipt)))`, including relay_signature. All chain/deletion/authorization fields MUST match that receipt. Witness arrays exist only in DeletionEvidenceBundle (§7.12.5), not in DeleteReceipt. Verify certified keys/membership against the pinned authorized heads. Witnesses are OPTIONAL: missing witnesses do not invalidate otherwise verified default admin or policy-permitted device authorization. They cannot substitute for it, grant chain-delete permission or form a new consensus/quorum. Multiple witnesses are collected only after explicit user confirmation via a locally authenticated exchange; no private key/token is published.

#### 7.12.4 DeviceCheckpoint

DeviceCheckpoint is `{type:"PALLASYNC-CHECKPOINT-v3",version:"3.0",checkpoint_id:uuid4,chain_id,generation:uint32,device_id:uuid4,relay_origin:origin,relay_key_id:b64u(32),log_id:uuid4,seq:integer,head_hash:b64u(32),parameters_hash:b64u(32),epoch_hash:b64u(32),transparency_id:uuid4,transparency_index:integer,transparency_hash:b64u(32),created_at_ms:ms,signature:b64u(64)}`. All fields are required, unknown keys rejected. #### 7.12.5 DeletionEvidenceBundle

DeletionEvidenceBundle is an unsigned public evidence container: `{type:"PALLASYNC-DELETION-EVIDENCE-v3",version:"3.0",chain_id,deletion_id:uuid4,delete_receipt_hash:b64u(32),witnesses:DeletionWitness[]}`. All members are required, unknown members rejected; witnesses has 0–128 entries, sorted by witness_device_id UUID bytes, with unique device IDs. The receipt is supplied separately, for example in an archive wrapper `{delete_receipt:DeleteReceipt,evidence_bundle:DeletionEvidenceBundle}`; this wrapper is not a signed protocol object or a new relay API.

Verify the original relay signature, ledger authorization, authorized parameter/epoch heads and local pins first (§17.11). Then compute the complete receipt's JCS hash, require bundle identity/hash equality, and verify each witness's matching identity/hash/authority fields, certified device signature and active membership at the authorized epoch. Created-at timestamps do not establish historical membership. A witness made after chain deletion uses the retained authorization-time registry proof, never a new enrollment. An invalid bundle/witness yields C_SCHEMA_VIOLATION or C_SIGNATURE_INVALID and retains public evidence; it cannot replace or invalidate independently valid deletion authorization. No witness count forms a quorum or changes erase permission. Removing a witness from an unsigned bundle loses evidence but cannot forge a witness signature.

There is no witness_signatures member in DeleteReceipt and no relay witness-submission endpoint. Generate bundles/witnesses only after the exact signed receipt is available and explicit local confirmation. Never modify receipt bytes or insert witnesses into a DELETE request/token. A later completion receipt has a different hash and requires its own bundle and new witnesses; old evidence remains bound to the old receipt. Local archives keep both versions independently.

After structural validation, clients and relays MUST enforce these semantic conditions:

Disclosed public-document capacity must permit two revalidations per chain request; operator/IP sharing limits may still cause visible 429 pauses, never bypass consent.
2. active_store, snapshot_store, attestations and deletion_ledger are present. replicated-durable and backup-durable require a present replica; copies.backup.present equals backups.enabled. backup-durable requires enabled backups, max_interval_ms <=86400000, a non-null restore-test interval <=7776000000 and non-null last successful test time, not later than publication. Other tiers must disclose their actual configuration without implying stronger durability.
3. Primary acknowledged history uses until_chain_deletion retention, subject only to separately authorized pruning; disclosure cannot introduce automatic history expiry. Every ciphertext copy's after_delete mode is erase or crypto_shred with a finite max_ms. With no backups, backup_delete_max_ms is null. Live/replica/WAL/snapshot copies finish within active_delete_max_ms; backup copies finish within backup_delete_max_ms. Every other copy class declares its own finite ciphertext deadline. 4. Required state, health limits/tier and actual authenticated quota agree with the disclosed effective configuration. Markdown remains the mandatory detailed human explanation, including copy access/protection and replacement steps; structured fields do not replace it.
5. Verify the pinned-key signature, exact origin/key, matching Markdown hash and monotonic revision. Retain the highest verified revision and complete disclosure hash per origin/key: a lower revision is rollback; the same revision with different complete JCS bytes/hash is equivocation. Never reset these pins automatically. The complete disclosure hash includes relay_signature. A changed Markdown body needs a new revision and signature. Published time is not a cryptographic freshness/completeness guarantee.

Both documents MUST represent the same current effective revision, published no later than its effective time; scheduled future versions belong to the declared archive/notice, not the current-document URLs. Announce each future change through those resources at least minimum_notice_ms before taking effect. A coherent pair may be accepted only when its effective_at_ms has arrived according to the client's corrected clock; clock uncertainty pauses rather than authorizing future terms. A mixed pair may be a publication race: at most one additional refetch of both is allowed per attempted chain request, then pause/backoff with C_RELAY_DISCLOSURE_INVALID if still inconsistent. No chain request occurs until a coherent pair is verified. Invalid/missing fields, signature/hash/revision failures or observed configuration mismatch cause C_RELAY_DISCLOSURE_INVALID; temporary fetch failures use C_RELAY_POLICY_UNAVAILABLE. Retain public signed contradictory evidence and local keys/outbox; policy changes do not create deletion authority. Operators cannot make missing mandatory values deployable by listing them as Open Questions.

## 8. Palleria Application Schemas

All schemas use §7.3's Operation and §15's full comparison key. A delete has `{}` body; clear has `{}` body and one of the declared scopes. Body fields below are REQUIRED unless marked O; unknown fields are rejected except `ext`. Booleans are actual JSON booleans. Numeric external IDs are canonical positive decimal strings in `entity_id` (`[1-9][0-9]*`, at most 32 digits); the `id` body field preserves the existing numeric shape where representable and is restricted to `1 … 2^53−1`. Larger IDs require a future schema; they MUST NOT be rounded or silently converted. This range is not inferred from a URL.

### 8.1 `palleria.favorite_tag/3`

`entity_id` is the NFC tag, 1–1,024 bytes, excluding `"*"`. Upsert body is `{"tag":string}` with `body.tag = entity_id`, and context contains the fractional `order_key`. Delete removes one tag; `clear` with scope `all` removes tags at or below the clear watermark. The live set is LWW by K. Display order is ascending `(order_key, K, entity_id UTF-8 bytes)`; a newly added tag is placed after the last live tag. Repeated add of a live tag MUST preserve its observed order key unless the user explicitly moves it. A concurrent move is a whole-entity LWW upsert. No automatic retention limit applies.

### 8.2 `palleria.search_history/3`

`entity_id` is the NFC query, 1–4,096 bytes, excluding `"*"`. Upsert body is `{"query":string}`, exactly equal to `entity_id`; context is `{}`. A winning upsert replaces the same entity's value and sets its derived `last_access_seq` (§15.6); it moves that one entry to the front without deleting any other entry. Delete removes the query; clear scope `all` applies a watermark. Default logical retention performs no automatic deletion. `MAX_SEARCH_HISTORY = 1_000_000` is the materialization safety ceiling (§16), not an automatic deletion count.

The reserved retention-policy upsert in §16.2 is also accepted, and is not a query entry.

### 8.3 `palleria.mute_settings/3`

`entity_id = kind + ":" + value`; `kind` is `tag`, `user`, or `illust`. Upsert body is `{"kind":enum,"value":string}`. Tag values are NFC strings of 1–1,024 bytes; user/illust values are canonical decimal IDs. A colon inside a tag belongs to `value`; split only at the first colon. Upsert adds a muted item, delete removes it; clear scope `all` resets this collection. LWW is per complete entity, with no union of losing bodies. No automatic retention limit applies.

### 8.4 `palleria.view_history/3`

This collection contains two disjoint scopes. `clear(all)` applies to both; `clear(seen)` and `clear(viewed)` apply only to the respective prefix. Unknown prefixes are invalid.

The reserved retention-policy upsert in §16.2 is also accepted, and is not a viewed/seen entry.

#### 8.4.1 `seen:<id>`

Upsert body is only `{"id":integer}`; its canonical decimal rendering MUST equal the suffix. It sets the feed-seen state, without requiring a move in any list. Delete marks it unseen. Only the winning upsert's minimal body and K need be in the membership index. Default logical retention performs no automatic deletion; `MAX_SYNCED_SEEN_ILLUSTS = 10_000_000` is the safety ceiling. Title, image URL, tags and artist data MUST NOT be included here.

#### 8.4.2 `viewed:<id>`

Upsert body contains `id:integer` (matching suffix) and OPTIONAL fields: `title:string` (≤4,096 bytes), `artistName:string` (≤1,024 bytes), `imageUrl:string` (≤4,096 bytes, HTTPS absolute URL), `pageCount:integer` (1–1,000,000), `type:"illust"|"manga"|"ugoira"`, `isBookmarked:boolean`, `xRestrict:integer` (0–2), `illustAiType:integer` (0–2), `tags:array` (0–1,024 NFC strings, each 1–1,024 bytes; no duplicates). Optional fields have no wire default: missing means unknown, not an instruction to merge with a losing body. The winning body is replaced atomically. `context = {}`. Each winning upsert moves the entity to the front by derived `last_access_seq`; repeated upserts retain one entry. Delete removes it. Default logical retention performs no automatic deletion; `MAX_VIEW_HISTORY = 1_000_000` is the safety ceiling. Details MAY be loaded lazily; their absence MUST NOT change existence or ordering.

### 8.5 `pallasync.device/3`

`entity_id` is a device UUIDv4. Only delete is allowed, with body `{}` and context `{}`. This is an encrypted lifecycle notification; it MUST NOT by itself revoke registry authority or erase verification keys. The authoritative revocation is the signed epoch transition (§18.4). A client marks a notice as confirmed only when that transition names the device. Unconfirmed notices are displayed in the audit UI and cannot trigger key deletion. Retain notices and device verification history until chain deletion.

### 8.6 `pallasync.audit/3`

`entity_id` is an event UUIDv4; only upsert with context `{}` is permitted. Body is `{"event":enum,"subject_id":string|null,"object_hash":b64u(32)|null,"result":enum}` with optional `ext`. Events: `enrollment`, `revocation`, `rotation`, `self_heal`, `migration`, `compaction`, `relay_migration`, `deletion`, `quarantine`. Results: `started`, `succeeded`, `failed`, `blocked`. Subject is at most 128 NFC bytes; hash refers to the relevant signed object when available. Authors MUST use a new event ID for each occurrence; exact duplicate replay is idempotent. Conflicting writes to the same ID still resolve by K but trigger an equivocation warning. Audit bodies MUST NOT contain mnemonic, root material, secrets or tokens. Audit is an encrypted application log, not a relay transparency proof. No automatic deletion or clear is allowed.

Recovery events additionally permitted in this Draft are `recovery_share_set_created`, `recovery_share_set_rotated`, `recovery_share_holder_added`, `recovery_share_holder_removed`, `recovery_ceremony_started`, `recovery_ceremony_succeeded`, `recovery_ceremony_failed`, `recovery_share_lost`, `recovery_share_compromised`. Use the existing body shape and `subject_id=null,object_hash=null`; place allowed metadata only in `body.ext["org.palleria.recovery"]`: `{recovery_set_id:uuid4,recovery_secret_fingerprint:b64u(32),threshold:integer,total_shares:integer,holder_kind:"device"|"offline"|null,holder_counts:{device:integer,offline:integer}}`. All fields are required, counts nonnegative/sum=n, t/n as §5.6; holder_kind is null for whole-set/ceremony events. Result remains the existing body.result, time remains Operation.created_at_ms. The extension stays within §3.6's 1024-byte limit. No holder IDs, wrap-key IDs, commitments, manifest/package/blob ciphertext, raw pieces, RMS, credentials, mnemonic/passphrase or root keys are allowed anywhere in recovery audit body/ext/context. This strict allowlist prevents arbitrary secret-bearing diagnostics from being encrypted and uploaded as audit. Audit ciphertext timing/size remains visible to the relay; absence of share upload does not hide all activity timing.

### 8.7 `palleria.chain/3`

`entity_id = chain_id`; only delete with `{}` body/context. This is a chain deletion notification, not independent deletion authority. Destructive action requires the authenticated deletion receipt or a deletion already initiated locally (§17.7). A device MUST NOT erase keys merely because an ordinary member uploaded this notification. An authorized deletion attempt can emit it before the deletion request; delivery is best effort. Its retention ends with chain deletion.

### 8.8 Schema Recognition

A receiver that does not implement a collection MUST retain its signed ciphertext and mark it `unsupported_collection` without applying it. This is `C_UNSUPPORTED_SCHEMA`, not corrupt data and not permission to delete it. Every conformant Palleria client implements §8.1–§8.7. All schemas obey the record-size ceiling, so a large viewed body MUST be reduced to supported optional fields before writing or rejected locally; it MUST NOT be truncated in transit. Extension collections require explicit versioned identifiers and deterministic conflict semantics; they cannot override these seven schemas.

## 9. Backward Compatibility and Migration

### 9.1 Isolation and Prerequisites

3.0 does not read or write 2.1 wire objects on v3 endpoints. Migration is a client-side read/decrypt/verify/convert/re-encrypt/re-sign process into a new 3.0 chain derived from the same validated mnemonic and passphrase (§5.1). New random device keys, fresh record UUIDv4 IDs and epoch 0 secret are REQUIRED. Legacy device keys, record signatures, salts, tokens, sequence numbers, AAD and ciphertext MUST NOT be reused as v3 authority or ciphertext.

The migration client first exports and verifies the old chain and takes a consistent legacy high-water mark. For a 2.1 random `chain_salt`, the old parameters or an enrolled old client/export are REQUIRED to locate/decrypt the old chain: the mnemonic alone cannot reconstruct a random legacy salt. Do not guess it. This legacy limitation does not change deterministic v3 recovery. Legacy rules are read only from [v2.1.md](./v2.1.md) and, for `/1`, [v2.md](./v2.md); they have no authority over v3 behavior.

### 9.2 Conversion

1. Verify legacy signatures and AEAD using the legacy version's rules. Quarantine failures; never relabel ciphertext or accept a failed signature under a different context. Resolve the frozen legacy state using its legacy conflict rules before generating v3 operations.
2. Normalize user identifiers to NFC in this explicit conversion step, deduplicate identical normalized identifiers, and record normalization collisions in the migration report. For a collision, use the legacy winning event; if legacy semantics cannot choose a winner, obtain a user choice and retain the source export. Ordinary v3 receive MUST NOT normalize signed content.
3. Convert `/2` live entities into `/3` upserts; preserve explicit legacy deletes as tombstones where their target exists. Legacy lifecycle notices become audit events only; they MUST NOT delete/revoke the new chain/devices.
4. Convert `/1` favorite/search arrays into one upsert per distinct item, mute arrays into one `kind:value` upsert per item, and seen/viewed arrays into one upsert per entity. Treat an authoritative replacement snapshot's absent entries according to legacy semantics; do not invent deletions from a truncated legacy snapshot. Parse legacy decimal-string `id` and `pageCount` exactly; reject overflow and invalid forms rather than round.
5. For a frozen final most-recent-first search/viewed list, emit upserts oldest to newest with increasing Lamports, so the newest obtains the largest derived `last_access_seq`. For favorites allocate ascending fractional keys in the existing list order. `seen` does not require order. Migration never uses legacy wall clocks to break ties. These initialization stamps are v3 stamps, not copied legacy sequence numbers.
6. Batch 1–1,024 operations into padded InnerRecords, bounded by §14.3. Each is signed by the newly enrolled migration device and uploaded normally. Data already automatically deleted/truncated by 2.1 cannot be recovered from that chain; report the missing range as unknown, never recreate it or claim completeness beyond the available export.

### 9.3 Failure, Resume and Completion

Persist a migration journal protected as local application data: source chain ID, source frozen high-water mark and export hash, destination chain ID/generation, conversion version, source entity-to-destination record mapping, fully constructed signed outbox records, accepted receipts and counts by schema. Do not put root material in this journal. Construct a record and journal mapping in the same local transaction, then upload. Retry the identical signed object after uncertain responses with a fresh token. Resumption MUST NOT allocate new IDs/stamps for an already journaled source item. If destination generation changes, stop and reconcile with re-seeding before resuming.

Completion requires: all source objects through the declared final mark processed, every conversion/quarantine decision reported, every resulting record durably acknowledged, and an independent v3 replay or verified snapshot matching canonical converted state including order, tombstones and clear floors. Write a `migration/succeeded` audit event. A claim of completion MUST state the source mark and any excluded invalid/unrecoverable data. A partially migrated chain MUST remain usable without being presented as complete.

### 9.4 Concurrent Legacy Writers and Retirement

Freeze old writes before final cutover. If the relay supports only ordinary reads/writes, stop all old clients or move to an immutable export; no nonexistent v2 freeze endpoint is assumed. While legacy writes remain possible, migration is provisional. After initial conversion pull a final legacy suffix, recompute affected legacy entities, and journal new v3 operations above the previous migration Lamport. Avoid accepting independent v3 edits to those entities during provisional conversion; if both sides were edited, report the conflict for explicit user resolution, rather than silently overwrite one side. There is no bidirectional bridge.

A completed cutover stops old synchronization and removes legacy authority from normal app paths. Keep the old export until the user has verified the new chain. Old chain deletion is a separate explicit user action using the legacy API; it MUST NOT delete the new chain. Upgrade or migration MUST NOT cause v3 `410 Gone`. The deprecation dates above are support-removal dates, not instructions to erase user data.

### 10.2 Genesis

`POST /chains`, A, body `{parameters:ChainParameters, device_record:DeviceRecord, epoch:EpochRecord, envelopes:EpochKeyEnvelope[]}`. ### 10.5 Registry and Revocation

`GET C/devices`, D/A; queries `cursor` and `limit` (§10.16). `200` page items are `{device_record:DeviceRecord,status:"active"|"pending_keys"|"revoked",enrolled_seq:seq,revoked_seq:seq|null}`. Verification keys/certificates are retained after revocation.

### 10.6 Upload Event Records

`POST C/records`, D, body `{records:SyncRecord[]}` (1–64). Every record MUST be authored by the token's device. Per-item results use `200` even with rejected items:

```json
{"accepted":[{"record_id":"<uuid4>","duplicate":false,"receipt":{"relay_seq":12,"received_at_ms":1791684000000,"kind":"record","object":{}}}],"rejected":[{"record_id":"<uuid4>","status":409,"code":"EPOCH_STALE","retryable":true}],"log_id":"<uuid4>","generation":0,"head_seq":12,"head_hash":"<b64u32>"}
```

The receipt's `object` is the complete submitted SyncRecord, represented by `{}` above only for brevity. `accepted` and `rejected` are REQUIRED arrays whose union contains every submitted ID exactly once; IDs within the request are unique. `duplicate` is boolean. Rejection item fields are exactly `record_id:uuid4,status:integer,code:string,retryable:boolean`. Items are processed in request order with independent durable commits; clients retry only rejected/transient items, never infer acceptance of missing IDs. Structural request errors, quota exhaustion before any item, oversized request and rate limit are top-level §19 errors. Once some records have committed, the relay MUST provide per-item outcomes; it MUST NOT return an ambiguous whole-batch rejection. Replay/dedup checks precede current-epoch checks for an identical already accepted record, but still require an authorized requester.

### 10.7 Peer Enrollment Offers and Approval

`POST C/enrollment-offers`, D, body `{request_id:uuid4,offer_nonce:b64u(32),expires_at_ms:ms}`. Expiry must be within 300000 ms of server time. `201` `{request_id,expires_at_ms,offer_hash:b64u(32)}`; the relay stores the offering device identity. Here offer_hash is b64u(SHA-256(JCS({chain_id,generation,request_id,offer_nonce,offering_device_id,expires_at_ms}))) using the stored authenticated offer values. The request expiry MUST NOT exceed the offer expiry. The local QR contains the full bound offer (§18.1).

`POST C/enrollment-requests`, no token, body EnrollmentRequest. Exact offer nonce, request ID, generation, expiry and self-signature REQUIRED. `201` `{request_id,status:"awaiting_approval",request_hash:b64u(32)}`; identical retry `200`; mismatched/replaced request `409 REQUEST_ID_CONFLICT`. `GET C/enrollment-requests`, D/A; cursor/limit; `200` page of `{request:EnrollmentRequest,request_hash,status:"awaiting_approval"|"approved"|"rejected",offering_device_id:uuid4}`. Only offering device or admin may read the pending request. `POST C/enrollment-requests/:request_id/approve`, offering D/A, body `{device_record,envelopes,admin_operation:AdminOperation|null}`. Subject device self-signs the DeviceRecord after receiving the signed certificate through the locally confirmed enrollment transcript; this step cannot be completed by the approving device alone. Verify request hash/certificate, policy and current epoch; `201` registry pending_keys response as §10.4. `POST C/enrollment-requests/:request_id/reject`, offering D/A, body `{request_hash:b64u(32)}`; `200` `{request_id,status:"rejected"}`. ### 10.8 Envelopes and Key Acknowledgement

`GET C/devices/:device_id/envelopes`, own D/P or A; queries `epoch`, `cursor`, `limit`. Device tokens may retrieve only their own device envelopes; A may retrieve any device envelope. `200` page of EpochKeyEnvelope objects. `POST C/epochs/:epoch/envelopes`, D/A, body `{envelopes:EpochKeyEnvelope[]}` of 1–128 device envelopes; recovery envelopes cannot be added here. `200` `{accepted:uuid4[],rejected:[{envelope_id:uuid4,status:integer,code:string,retryable:boolean}]}`. Only senders holding the epoch secret can construct valid envelopes; recipient eligibility is checked by the relay and client.

`POST C/devices/:device_id/keys/ack`, own D/P, body `{epoch_hash:b64u(32),epoch_commitment:b64u(32)}`. Acknowledgement attests that the subject has locally verified the envelope; a relay cannot prove that decryption occurred. Current epoch hash/commitment MUST match; `200` `{device_id,status:"active",epoch_hash}`. `409 EPOCH_STALE` requires retrieval/verification of the new envelope and fresh acknowledgement. P's only other allowed routes are GET parameters, GET its own envelopes and GET epochs; P MUST NOT upload/download records or approve enrollment. D may repeat acknowledgement after rotation.

### 10.9 Event Pull and Log

`GET C/records`, D/A; queries `after_seq` (default 0), `cursor`, `limit` (default 200), and OPTIONAL `collection_tag` with `epoch` together in queryable profile. `200` `{items:LogEntry[],next_cursor:string|null,has_more:boolean,scan_through_seq:integer,log_id:uuid4,generation:uint32,head_seq:integer,head_hash:b64u(32)}`. A filtered stream MUST NOT advance the global fully-verified cursor. `private` rejects collection filters with `400 FILTER_NOT_ALLOWED`.

`GET C/log`, D/A, queries after_seq/cursor/limit; same response shape, includes all control and record entries in ascending relay_seq. The sequence is gapless within a retained suffix; pruning is explicitly reported. `GET C/log/head`, D/A, no query, `200` `{log_id,generation,head_seq,head_hash,min_available_seq:seq,epoch_hash,parameters_hash}`. `409 LOG_PRUNED` includes a snapshot reference in `context`; `409 LOG_ID_MISMATCH` requires §17.3 repair/bootstrap.

### 10.10 Epoch Read and Commit

`GET C/epochs`, D/A/P; cursor/limit; `200` page items `{epoch:EpochRecord,epoch_hash:b64u(32),committed_at_ms:ms,relay_seq:seq}`. `GET C/epochs/:epoch`, same authorization, `200` one such item.

`POST C/epochs`, D/A, body `{expected_epoch_hash:b64u(32),epoch:EpochRecord,envelopes:EpochKeyEnvelope[],admin_operation:AdminOperation|null}`. Ordinary manual/scheduled/key_rotation uses null; emergency/revocation follows its administrative requirements. `201` `{epoch_hash,receipt:LogEntry}`. The exact complete bundle is committed by CAS; `409 CAS_MISMATCH`, `409 MEMBER_SET_MISMATCH`, `409 RECOVERY_ENVELOPE_REQUIRED`, `403 ROTATION_NOT_ALLOWED`. Retry after a lost response first checks whether its epoch_hash is already the head or a committed ancestor; an identical committed bundle returns `200` without rotating twice. New epoch, parameters, registry and current write epoch become visible atomically.

### 10.11 Snapshot Store

`POST C/snapshots/parts`, D/A, body `{records:SyncRecord[]}` (1–64), `200` `{accepted:uuid4[],rejected:[{record_id,status,code,retryable}]}`. Device token requires its own signed parts; A can restore verified historical parts during re-seed/migration. They are immutable and isolated from normal event pull. Staging alone changes no client state and assigns no event-log sequence. `GET C/snapshots/parts/:record_id`, D/A, `200` `{record:SyncRecord}`; missing `404 SNAPSHOT_PART_NOT_FOUND`.

### 10.12 Compactions and Bootstrap

`POST C/snapshots`, D/A, body `{compaction:CompactionRecord}` referencing staged parts. Device signer must be active. `201` `{compaction_id,receipt:LogEntry}`; missing/hash-conflicting part `409 SNAPSHOT_INCOMPLETE`; stale generation/log `409 LOG_ID_MISMATCH`. `GET C/snapshots`, D/A, cursor/limit; `200` page of CompactionRecord objects. `GET C/snapshots/:compaction_id`, D/A, `200` `{compaction:CompactionRecord}`.

`POST C/log/prune`, A, body `{compaction_id:uuid4,through_seq:integer,admin_operation:AdminOperation}`; prerequisites §16.7. `200` `{min_available_seq:seq,compaction_id}`. `409 COMPACTION_UNSAFE` if it would discard the sole verifiable history, snapshot, tombstones, required epoch/registry evidence or unretrievable data. Ordinary compaction does not auto-delete an event log.

### 10.13 Repair Upload

`POST C/records/repair`, A, body `{source_log_id:uuid4,records:SyncRecord[],receipts:LogEntry[]}`; both arrays 1–64 and one-to-one. Validate retained historical signatures, generation/epoch and subject enrollment at acceptance against the supplied verified source history. `200` outcomes as §10.6 plus `repair_required:boolean`. If the restored relay cannot prove historical acceptance, return `409 REPAIR_PROOF_REQUIRED`; it MUST NOT silently treat a revoked author's old ciphertext as a new live write. Use §17.5 re-seeding of a verified materialized state when original receipt proof is unavailable. Repair into an already newer generation does not append older-generation application events; it returns GENERATION_MISMATCH and requires another explicit verified-state re-seed if that historical input must be included. Device upload to this route is `403 ADMIN_REQUIRED`.

### 10.14 Export and Shutdown Notice

`GET C/export`, D/A; queries `cursor`, `limit` (default 200; max 1000); `200` export media type (§17.4). A can additionally request `include_recovery=true`; D MUST NOT request it. All chunks contain metadata plus bounded items and a continuation marker; the cursor pins the source high-water mark. `GET C/relay-notice`, D/A, `200` `{shutdown_at_ms:ms|null,migration_origin:string|null,notice_id:uuid4,server_time_ms:ms}`. A notice never deletes data or changes epoch authority and MUST NOT induce key erasure. Clients require explicit destination selection and §17.6 validation before contacting it for chain operations or minting fresh audience-bound tokens; notices cause no automatic data/token transfer.

### 10.15 Delete Chain

`DELETE C`, A or D only if `allow_device_chain_delete=true`; body `{deletion_id:uuid4,expected_parameters_hash:b64u(32),expected_epoch_hash:b64u(32),admin_operation:AdminOperation|null}` (admin REQUIRED for A, null for permitted D). Both body hashes MUST match current CAS heads and, for A, the AdminOperation preconditions. `202` `{deletion_id,state:"deleting",assurance:"crypto-shred"|"backup-expiry",delete_after_ms:ms|null,receipt_hash:b64u(32)}`. The relay durably records a deletion ledger entry before denying further chain operations. After that, authenticated requests to C return `410 CHAIN_DELETED` with deletion context; exact duplicate deletion returns its original receipt. §17.7 defines the meaning and verification limits. `GET C/deletion`, A or the recorded authorized deleting device, returns the ledger receipt even after deletion; other tokens are not accepted as proof of deletion authority. This is the only post-deletion read route. A temporary outage, old generation, unsupported version, restored log or moved relay MUST NOT produce 410.

### 10.16 Pagination, Cursors and General Outcomes

Generic page body is `{items:array,next_cursor:string|null,has_more:boolean,log_id:uuid4,generation:uint32,head_seq:integer}`. `limit` is a decimal 1–1000; `after_seq` is decimal 0–2^53−1. Cursor is an opaque ASCII Base64URL string ≤2,048 bytes, authenticated by the relay, binding chain, generation, log_id, resource, filter, pinned head and last scanned position. It expires no sooner than 24 hours after issuance. `cursor` and `after_seq` are mutually exclusive; request limit MAY be changed on continuation but filters MUST match. Items never exceed limit; `has_more` iff `next_cursor != null`. No more items returns `next_cursor:null,has_more:false`. Deleted entries during staging/registry pagination are handled against the pinned view, not offset pagination. `409 CURSOR_EXPIRED` restarts from the locally committed scan mark; `400 CURSOR_INVALID` rejects tampering/incorrect binding. The relay MUST cap response bodies at 8 MiB even if that gives fewer than limit entries; it MUST make forward progress or return a typed oversized-item error.

JSON requests with the wrong media type return `415 UNSUPPORTED_MEDIA_TYPE`; empty body is allowed only for GET. No GET endpoint accepts a body. `404 CHAIN_NOT_FOUND` for an authenticated unknown chain does not authorize automatic registration. `403 DEVICE_REVOKED` stops ordinary sync; `403 DEVICE_PENDING_KEYS` invokes §10.8. `429 RATE_LIMITED` always includes Retry-After; `507 QUOTA_EXCEEDED` and `507 STORAGE_UNAVAILABLE` are distinct. All remaining errors and retry classifications are §19.2. HTTP examples are illustrative; only Appendix C values are test vectors.

### 10.17 Attestation Responses and Transparency Reads

Every successful mutation that appends one or more LogEntries, or stores new immutable snapshot parts, adds REQUIRED `upload_receipts:UploadReceipt[]` in its existing response wrapper, in ascending relay_seq for log entries or record_id for snapshot-part receipts, covering all newly committed objects or the original bundle on exact duplicate retry. This includes genesis/re-seed, enrollment approval, revocation/epoch/envelope commits, record/snapshot-part uploads, compaction and repair. Existing `receipt:LogEntry`, accepted/rejected fields and unsigned wrappers remain; receipts do not replace client signatures. A successful state-only operation with no new LogEntry has no upload_receipts requirement. Staging import, offer/request rejection and key acknowledgements do not fabricate log receipts. Acceptance's durability/signature rule is §17.9. Snapshot-part receipts have the §7.12.1 null sequence/entry-hash form and signed transparency inclusion but no data-log inclusion. GET C/snapshots/parts/:record_id additionally returns its original `upload_receipt:UploadReceipt` beside the signed record; duplicate store upload returns the same receipt. A complete committed CompactionRecord is still required for valid snapshot/bootstrap coverage. Repair receipts name their new log_id/seq; original receipts remain source evidence.

`GET C/receipts/:relay_seq`, D/A, query `log_id:uuid4` REQUIRED and no other query/body, `200` `{entry:LogEntry,receipt:UploadReceipt}`. 409 LOG_ID_MISMATCH if not the current retained incarnation, 404 RECEIPT_NOT_FOUND if no such accepted sequence is known. A pruned entry returns `200` `{entry:null,receipt:UploadReceipt}`; entry type is thus LogEntry|null and the client needs compaction/pinned historical entry evidence for full H recurrence. Exact receipts survive pruning. Receipt absence is pending evidence, not authority to discard an outbox/accepted record. Only current log_id is queried here; original-incarnation evidence is retained in exports/local archives.

`GET C/transparency/head`, D/A, no query/body, `200` `{head:RelayTransparencyHead}`. `GET C/transparency/entries`, D/A, queries `transparency_id:uuid4` REQUIRED, `after_index:integer` default 0, `through_index:integer` optional (default current head index), `cursor` optional and `limit` default 200/max 1000. Range must satisfy 0<=after<=through<=pinned current high-water index. 200 `{items:RelayTransparencyEntry[],head:RelayTransparencyHead,anchor_index:integer,anchor_hash:b64u(32),next_cursor:string|null,has_more:boolean}`. Initial anchor is the requested after_index/T at it; subsequent page anchor is its previous page end. Cursor pins origin/chain/transparency_id/start/through/head hash and uses §10.16's opaque authenticated format/expiry/conflict checks. Head is the signed high-water cut, not regenerated from each page's current server time; through_index is exactly that head.entry_index. Choosing an older cut requires a stored matching signed head, otherwise 409 TRANSPARENCY_RANGE_UNAVAILABLE. Incorrect incarnation is 409 TRANSPARENCY_ID_MISMATCH. Client checks its pinned anchor and streams the entire range to that head for inclusion/consistency (§17.9); no constant-size Merkle proof is claimed. An unavailable prefix cannot be skipped without explicit independent trust/reconciliation.

All three routes use fresh Capability Tokens with exact path/query/audience, normal read rate limits and §19 problems. Post-deletion they return 410 as other chain reads do; GET C/deletion is still the sole post-deletion route and includes the final minimal deletion attestation. No recovery/share endpoint is added. No public or anonymous chain-ID proof endpoint exists in this Draft.

## 11. Client Synchronization Lifecycle

### 11.1 Worker and Outbox

On local edit, transactionally allocate the next Lamport/device_seq, construct the immutable signed record, and store it in the durable outbox together with its provisional materialization. Store the signed predecessor before constructing the next record. Abandoning a sequence after construction MUST NOT cause reuse; retain the abandoned signed record for repair or rebuild an unaccepted suffix with new IDs and consistent predecessor links. An outbox entry is deleted only after its exact hash has a durable UploadReceipt whose relay signature and object/log bindings verify under the pinned origin key; preserve that immutable receipt and its pending/verified inclusion status. Missing linking evidence is shown as pending and never silently resets a pinned prefix. Crash after relay commit and before local acknowledgement is handled by exact duplicate retry. Never re-encrypt the same record ID with different content.

Before any chain request the worker passes §11.7's current-policy/consent guard; pending or withdrawn consent suspends network synchronization without clearing local state. It then obtains current signed parameters, epoch/registry updates and checkpoints, retrieves its envelopes, validates them, then drains a bounded outbox and pulls a bounded log page. It persists raw signed objects, validation results, materialized changes and the page cursor atomically. A transient failure does not clear state. Each authenticated retry has a fresh token. Rejected stale-epoch, unaccepted records are rebuilt under the new epoch with fresh record IDs/nonces/device_seq and Lamports above known state; superseded outbox objects are kept until their lack of acceptance is resolved. Already accepted old-epoch records are never rewritten as a retry.

### 11.2 Receive Pipeline and Independent Progress Marks

Validate, in order: UTF-8/JSON limits; chain/generation/log binding; required authority history; outer signature; record/AAD consistency; epoch envelope and commitment; AEAD; padding frame; InnerRecord/schema; then apply K-based state changes transactionally. Resolve a missing ancestor, device certificate, key or snapshot part by bounded fetch before labeling corrupt data. Valid records with a predecessor gap may be applied; retain the gap and compare the predecessor hash when it arrives. A gap in authored device_seq may also represent an unaccepted/abandoned outbox item; it is best-effort withholding evidence, not proof that an accepted relay entry is missing. Contiguous relay-prefix verification and author-gap status are tracked separately. A conflicting predecessor/sequence is quarantined as equivocation. One quarantined record MUST NOT block all unrelated entities, but its effects MUST NOT be applied or counted as verified.

Maintain distinct marks: `downloaded_through_seq` (persisted bytes), `verified_through_seq` (contiguous authenticated/eligible/decrypted or snapshot-covered prefix), and `materialized_through_seq` (that verified prefix applied or indexed). Filtered/priority downloads have their own cursor and MUST NOT advance these global marks across unprocessed entries. Resume from durable marks after crash; do not rely on an HTTP cursor alone. Progress is reported as downloaded/verified/applied counts against a pinned head, plus outstanding gaps and bytes; it MUST NOT claim 100% on a filtered recent view.

### 11.3 Bootstrap and Offline Priority

A new or long-offline client first satisfies relay-policy consent (§11.7) for any network source and explicit initial-source selection (§11.6) where no local pin or known peer exists. It can then load a verified snapshot (§16.6), prioritize recent search/viewed index pages and seen membership, then fetch details/older state in the background. Under `private`, the relay cannot select “recent history”: priorities are determined from the encrypted snapshot manifest after client decryption, or from local indexes. Under `queryable`, tag filters narrow collections only; they do not reveal operation order or entity IDs. Without a snapshot, a client streams the event log and builds an on-disk index; it cannot assert complete seen membership before all relevant events are applied. Offline edits are permitted, but remain unaccepted until current authority/epoch is verified. Workers MUST support cancellation, bounded transactions, restart and visible progress.

### 11.4 Independent Recovery Ceremony Lifecycle

Recovery is never a sync-worker repair action, background task or automatic response to 404/410/revocation/relay notice. Only explicit user action enters selecting_holders from idle. Select a known set and intended privileged operation; show t,n and usable distinct holder count H. Below t fail with C_RECOVERY_THRESHOLD_NOT_MET without deleting a package. Prompt each holder's local authentication, establish a separate live SAS session for every piece transfer (§7.11.5), including the trusted offline reader, then enter collecting_shares. The collector's own piece may be locally unlocked after explicit confirmation; it does not count as a transfer or bypass one-share-per-device storage.

Reject noncanonical fields, signature/hash/commitment failures, duplicate physical holders/indexes and mismatching set/chain/generation/fingerprint/blob/manifest before interpolation. Known retired/compromised sets are refused for ordinary ceremonies; the narrowly confirmed compromised-set emergency new-root migration in §18.7 is the sole exception. Require a verified active status chain for ordinary recovery and compare all holders' known status heads; an offline/isolated set may lack a later retirement, so the UI MUST disclose unavailable status freshness instead of promising globally current recovery. A future generation of the same chain does not rewrite old package generation; validate original binding, then separately verify current parameter/epoch ancestry after recovering root. Refuse a conflicting chain/admin pin.

| State | Entry/transition guard | Failure handling |
|---|---|---|
| idle | Explicit user starts a ceremony; no secret session exists. | Background worker cannot enter it. |
| selecting_holders | Valid parameters/set and planned operation; H>=t. | Insufficient pieces remain operational, not chain corruption. |
| confirming_sas | Two authenticated/unlocked local endpoints; exact descriptors; both confirm live SAS. | Mismatch/timeout/cancel clears session buffers and returns failed/cancelled. |
| collecting_shares | Valid collect_share payloads, unique indexes/holders; explicit confirmation per transfer. | Preserve original packages; reject this input, display safe error. |
| reconstructing | At least t consistent pieces; interpolate lowest t indexes and check any extras. | Never brute-force subsets or ignore a bad piece. |
| verifying_secret | Immediately zeroize collected raw-share buffers, decrypt blob with RMS, validate frame/input/checksum/fingerprint/all bindings and derive chain/admin identity. | Wrong passphrase/identity is failure; no root operations permitted. |
| authorized | All secret/identity checks pass; ephemeral mnemonic-holder session established. | This grants root inputs only, not permission to ignore epoch/registry/checkpoint conflicts. |
| performing_operation | User confirms the named operation, current authority history/CAS preconditions verified. | Usual §10 errors apply; retain sync data/outbox. |
| succeeded / failed / cancelled | End, cancel, timeout or error. | Zeroize RMS, plaintext blob, inputs, derived root keys and all session keys; queue only sanitized result audit. |

A setup threshold test (§18.6) is a separate purpose=create/rotate session under an **already established** mnemonic-holder dealer session. It may use that dealer's prepared manifest/status solely to test stored-piece readback, interpolation and identity equality; it MUST NOT enter authorized or authorize a new root operation from a prepared set. The dealer acting as test collector uses the collector role for those pair sessions. All usual local authentication/SAS, integrity, no-persistence and zeroization rules apply. Failed readback prevents activation. No ordinary restore may use this setup exception to bypass the active-status guard.

There is no durable resume of collected pieces or reconstructed root inputs. On interruption/restart collect again. Five-minute pair-session expiry requires a new live SAS pair; five minutes without user interaction during collection aborts the ceremony. A long authorized user operation follows its own explicit session lifetime, not unattended worker access. Best-effort safe memory handling is §7.11.3. Persist only public progress/error metadata, never a resumable encrypted full RMS/root stash.

Identical retransmission is idempotent and counts once. Reusing an index with another purported piece or counting one holder twice is C_RECOVERY_SHARE_ALREADY_USED; set mismatch is C_RECOVERY_SET_MISMATCH. After blob decryption, derive original §5 keys and constant-time compare fingerprint/chain/admin to manifest and existing pins. No trial-and-error passphrase guessing or relay validation oracle is part of recovery. Collectors do not persist other holders' packages: even ciphertext temporary copies are excluded from logs/backups.

Audit started/succeeded/failed through §8.6. If collector is not yet enrolled, keep only the permitted sanitized audit metadata locally until an approved newly generated device can publish it. Failed or unavailable audit upload never blocks zeroization/emergency action. Recovery never supplies missing application ciphertext by itself.

### 11.5 Consistency Probes and Honest Progress Display

Clients MUST run a bounded probe when starting/resuming a sync worker, after an upload's uncertain outcome, before destructive actions/cutover, and while active at a default 15-minute interval with uniform 0…20% positive jitter. The user may choose a longer interval for power/network cost; display disabled/deferred probes and last successful comparison time. Offline or OS scheduling delays mean no real-time detection guarantee. Limit to one probe in flight, use §17.8 backoff/rate limits and fresh audience-bound tokens, and coalesce probes with existing pulls. A timer never starts a Recovery Ceremony.

Fetch GET C/log/head and GET C/transparency/head, verify pinned origin/key/signatures and compare their immutable views against protected checkpoints/receipts. Fetch necessary bounded GET C/epochs, parameters, registry/log pages and GET C/receipts/:relay_seq to reconcile a changed head. Concurrent advancement between two reads is not a contradiction: compare at a shared prefix or repeat once, then report unresolved evidence. Check log_id/incarnation, hash consistency, epoch/parameter ancestry, own accepted record hashes and the stored device_seq tail, and min_available_seq against the authorized CompactionRecord. A sequence increase in min_available_seq requires verified pruning evidence; LOG_PRUNED alone is insufficient. Do not demand that a global relay head_seq numerically equals device_seq: different namespaces. Compare the exact authored record/hash and acceptance evidence instead.

On positive contradiction (fork, rollback, key change, incompatible receipt/head/epoch/deletion evidence), suspend affected writes and destructive actions, retain local data/keys/outbox, store signed evidence in protected quarantine, warn, and request independent peer/checkpoint/export reconciliation (§19.4). Timeout, missing record/proof or unchanged tail is pending evidence, not automatic proof of malice; report C_MISSING_DEPENDENCY/transport failure and retry. Evidence-based repair/re-seed requires the ordinary explicit authorization. A valid verified deletion follows §17.7; an unverified 410 always preserves secrets/data.

The UI MUST show device_seq/prev_record_hash gaps as possible missing author history, retain gaps for later fill and distinguish an abandoned unaccepted suffix. Show verified-through *observed/pinned* head, unresolved gaps, filtered downloads and time of last independent head comparison. Do not label a filtered view or isolated relay assertion as globally “fully synchronized”. After 30 days without an enrolled peer's independently authenticated checkpoint, offer a local peer/head comparison; inactivity alone does not prove withholding. Exported receipt/head evidence or physical peer exchange provides independence; relay head advertisements alone do not.

### 11.6 Initial Recovery Trust-Source Selection

When no protected local checkpoint/pin or independently authenticated known peer is available, a client MUST enter source_selection_required and obtain explicit user selection of the initial checkpoint/snapshot/history source before installing bootstrap state, establishing its first history pin or authoring based on it. Sources may be a user-selected authenticated relay, a locally verified export or an independently authenticated peer. There is no protocol-wide automatically trusted initial relay/snapshot author. Highest sequence, newest timestamp, a relay notice, valid TLS or the relay's own signature does not automatically choose one.

The client MUST display source kind/reference, expected chain_id/admin-key fingerprint, verified available parameter/epoch heads, log/prefix and snapshot hashes/coverage where available, and the absence of independent freshness/completeness evidence. Record the user's explicit source choice and the observed public hashes in protected local bootstrap state; persist no root material. Policy consent and trust-source choice are separate decisions: agreeing to privacy.md never implicitly trusts a checkpoint/snapshot. A combined screen may collect both only as clearly identified, initially unselected affirmative choices. Dismissal, timeout or background recovery is not a source choice; return C_BOOTSTRAP_TRUST_REQUIRED and retain downloaded staging/local data.

Source selection never waives checksum/derived identity, certificate/authority history, signature, AEAD, snapshot-state validation, existing checkpoint conflict or authenticated-deletion checks. If no independent initial pin exists, full replay/recomputation validates the supplied input but cannot prove that the source omitted no unseen tail. Accepting a snapshot without full replay requires the user explicitly trusting its authenticated authorized source/author under §16.6; show that its semantic completeness remains a source-trust assumption. Do not create evidence that was not received or claim globally complete recovery. A failed or contradictory source is not installed and cannot overwrite a known pin. An offline export/local ceremony alone sends nothing to a relay; any subsequent relay access separately requires §11.7 consent.

### 11.7 Mandatory Relay-Policy Consent

Every client MUST provide affirmative user consent to each relay's current operator-specific privacy.md and signed privacy.json (§17.12/§7.13) before any chain API request, including genesis, import/enrollment, pulls/uploads, recovery reads, exports, administrative requests and deletion. Before consent, only anonymous health and policy fetches at the explicitly selected origin are permitted; do not mint/send Capability Tokens or send chain/device IDs, ciphertext, recovery material or application authentication/Cookie data. Local viewing, editing/export and explicitly authorized local recovery remain available.

Before each chain HTTP request, fetch/revalidate the current policy from `${relay_origin}/privacy.md` and the signed structured disclosure from `${relay_origin}/privacy.json` over HTTPS, then validate the complete pair under §7.13. Both resources are anonymous public documents; use no Capability Token, account or chain identifier. JSON is application/json with a decoded 1 MiB ceiling. Schema/signature/binding/revision failures pause with C_RELAY_DISCLOSURE_INVALID; successful HTTP retrieval alone is insufficient. A same-origin 304 may reuse the exact previously validated cached bytes; an unavailable, oversized, invalid-UTF-8 or cross-origin response is C_RELAY_POLICY_UNAVAILABLE and pauses the request. Never treat a cached document as current after failed revalidation. Conditional caching reduces body transfer but does not skip the guard; operator policy-request limits MUST permit this workflow. Do not follow a policy's links or load remote images/scripts automatically. Render Markdown with raw HTML/execution disabled. A public policy response, even 410, is not authenticated chain-deletion authority.

Compute `policy_sha256 = b64u(SHA-256(exact UTF-8 body bytes after HTTP Content-Encoding decoding))`; do not normalize Unicode, whitespace or newlines, and do not use JCS. Show the complete policy, origin, operator/revision information, quota/rate/durability/copy/deletion disclosures and current relay key fingerprint, with no preselected agreement. Only explicit affirmative user action persists LocalConsentRecord: `{consent_id:uuid4,relay_origin:origin,relay_key_id:b64u(32),policy_url:string,policy_sha256:b64u(32),disclosure_url:string,disclosure_revision:uint32,disclosure_sha256:b64u(32),accepted_at_ms:ms,withdrawn_at_ms:ms|null}`. Every field is required; policy_url exactly equals origin plus `/privacy.md`, disclosure_url equals origin plus `/privacy.json`, disclosure_revision matches the verified object, and disclosure_sha256 is b64u(SHA-256(JCS(complete signed RelayPrivacyDisclosure))). Retain both accepted documents locally for review. Earlier Markdown-only consent records are insufficient and require explicit renewal. This is unsigned protected local state, not a SyncRecord, token, relay identity/account or uploaded audit event. Persist consent atomically before minting a fresh token; time fields are display/audit data, not trusted ordering. An active record has withdrawn_at_ms=null and exact current origin/key/Markdown-hash/disclosure-hash/revision matches.

No matching consent, initially unprovisioned consent or a changed policy body or signed disclosure enters consent_required and returns C_RELAY_POLICY_CONSENT_REQUIRED. A revision label that stays unchanged cannot preserve consent when the body hash changes; even editorial body changes or structured disclosure changes require renewed affirmative consent. New origin, migration or independently verified relay-key replacement also requires consent for that exact new binding. C_RELAY_KEY_MISMATCH remains a separate trust suspension: agreement to a policy never auto-accepts a new relay key. Revalidate again after an interactive wait before dispatch; changed documents restart consent rather than silently using stale approval. This check covers the last successfully obtained version, not cryptographic proof that a malicious operator disclosed every change.

Users MUST be able to inspect accepted policies/records and withdraw consent. Rejection, dismissal, timeout, withdrawal, app upgrade, device replacement or background work cannot manufacture consent. Pending/withdrawn consent blocks every remote chain request; preserve local keys, packages, outbox, state and unsent changes. Local export remains possible, and another relay requires its own explicit selection/consent/migration verification. Withdrawal is not chain deletion. Do not auto-delete, re-enroll, send to another origin or resume online requests as an error-recovery shortcut. Capacity errors saving local consent retain this paused state. First-time bootstrap also needs §11.6 source selection. The policy guard MUST NOT interrupt zeroization or erase authority evidence.

## 13. Epoch Lifecycle

### 13.1 Genesis and Independent Secrets

Epoch 0 is random and has null predecessor, not `HKDF(prk, 0)`. Generate a new secret for every rotation; do not reuse the old one or derive the new from any retained key. Compute the commitment, encrypt one envelope to each prospective member plus one recovery envelope, sign them, then sign the EpochRecord naming the recovery hash. Epochs form an immutable hash chain across generations. Only one epoch is writable. Ordinary event upload at an old epoch is `EPOCH_STALE`; retention of its key does not grant write authority. A client MUST verify all missing epoch ancestors or a previously authenticated checkpoint before accepting a newer head.

### 13.2 Distribution and Activation

After commit, each member downloads its own envelope, verifies the complete binding and commitment, securely persists the secret, and acknowledges the current epoch (§10.8). Until it has done this locally it MUST NOT author under the new epoch. Members that were active remain registry active across ordinary rotation; pending devices remain pending until acknowledgement. A missing envelope for a named member is a failed atomic bundle (`MEMBER_SET_MISMATCH`), not a reason for that member to derive a key from the mnemonic. Approvers can add HPKE envelopes for newly enrolled devices without changing an epoch, subject to historical eligibility; they cannot send any epoch key to a revoked or unapproved device.

### 13.3 Authority and Recovery-Envelope Requirement

Admin authorizes genesis, emergency rotation and re-seed. Active devices may sign manual, scheduled, device_revocation and key_rotation epochs when `allow_device_rotation=true`. Revocation changes are committed with the epoch and cannot be scheduled separately from secret replacement. Enrollment changes are approved by certificate, and the epoch member list at a later rotation MUST reflect the then-current approved membership. A compromised active member can corrupt application state and, if policy allows, approve a device/rotate keys; these are limits of device authority, not relay-only privileges.

Every new epoch MUST include a valid recovery envelope. Because §5.5 forbids persisting `recovery_kek`, **creating an epoch requires a mnemonic-holder session to produce that envelope**, including device-signed rotations. The ordinary device cannot manufacture it from an old envelope. The mnemonic holder can generate/encrypt the new secret within the authorized session and have the permitted device sign the final bundle; root material is then zeroized. The relay verifies signatures/bindings but cannot test recovery decryption; the mnemonic holder MUST open the envelope and verify the commitment before commit. Other clients verify their own device envelopes. Losing recovery decryptability due to a malicious authorized writer remains detectable only with the mnemonic/verification transcript. No unattended deterministic derivation or persisted recovery key is introduced to hide this requirement.

A successful explicit Recovery Ceremony (§11.4) may establish the same transient mnemonic-holder session after all secret/identity checks, permitting recovery-envelope creation, emergency revocation or re-seeding under their existing authority/CAS rules. It does not add an epoch-derived recovery key, unattended rotation, automatic enrollment or a checkpoint reset. Failed/partial recovery grants no authority; scheduling a due rotation MUST NOT trigger a ceremony automatically.

### 13.4 Commit, CAS and Emergency Revocation

Read the current parameter hash, epoch hash and registry. Build the complete next bundle against that view. At commit compare `expected_epoch_hash`, generation and, for an AdminOperation, `expected_parameters_hash`; require next epoch number, correct predecessor, exact post-revocation member list and complete envelope set. A durable transaction writes the ordered control entries, updates registry/current epoch and publishes the new head. A rejected CAS publishes nothing. Two proposals from the same predecessor cannot both commit on an honest relay. A loser discards its unpublished secret securely, fetches the winning head, and rebuilds from fresh randomness; it MUST NOT reuse a failed secret for a different epoch/binding.

Emergency admin rotation can revoke any device, including every previous device, while enrolling at least one fresh recovery device in the same transaction. That new DeviceRecord has an admin certificate and device self-signature. The bundle can include such `device_records` as an OPTIONAL array in the emergency epoch/revocation request only; the AdminOperation target payload includes this array when present. An emergency EpochRecord with no revocation/re-seed is authorized by its admin signature and A token and uses admin_operation null; when devices are revoked, a revoke_device AdminOperation is REQUIRED and its target includes any device_records array. No ordinary device can exercise this override. Registry/epoch membership is validated after staging the new certificate. With no valid member, the bundle is rejected. Snapshot/key coverage rules in §13.5 still apply: emergency security does not justify silent history loss.

### 13.5 Old-Epoch Retention Profiles

Profiles regulate old secrets/envelopes and reconstructability, not routine deletion of history entries. Ciphertexts may remain in immutable logs after keys expire, but their application state MUST remain accessible through a complete newly encrypted snapshot before expiry. A revoked device can retain old keys under every profile (§20.2).

| Profile | Key/envelope handling | State/history prerequisite |
|---|---|---|
| `retain` (default) | Retain historical recovery envelopes and keys; deliver old device envelopes to approved new devices. | Full replay/export possible for all retained epochs. |
| `windowed` | Old epoch eligible for expiry at its successor's committed_at_ms plus epoch_window_ms. Clients cease distributing expired old keys; relay removes old recovery/device envelopes only after safe handoff. | Before expiry, complete state including cold histories, deletes, clear/retention registers and author counters MUST be re-encrypted in a snapshot under a retained current epoch. If unavailable, postpone expiry and display `rotation_retention_blocked`. |
| `immediate` | Old keys become non-distributable after the new epoch's complete state snapshot is durable and verified; then compliant devices erase old cached secrets and relay removes old envelopes. | Rotation is not considered retention-complete until that snapshot exists. On incomplete handoff keep keys and restrict new enrollment; do not silently lose history. |

The snapshot is built from a fully verified old prefix and all post-rotation records through a chosen new-prefix mark. CAS prevents publishing it for the wrong epoch. Live writes may continue, then bootstrap applies the suffix above coverage. There is no requirement to decrypt all history at once in memory; the re-encryption streams parts. Removal of old keys makes raw old operation bodies unrecoverable through the protocol even though materialized history remains. A client/UI/export MUST label such archival-event loss. The relay reports `HISTORY_KEY_EXPIRED` to authorized requests for removed envelopes; clients bootstrap from the new snapshot rather than quarantine old ciphertext as an AEAD failure. Clients MUST NOT erase keys based only on a relay clock claim without locally verifying the durable handoff and pinned head.

### 13.6 Scheduled Rotation

If scheduled_rotation_ms is nonzero, the relay committed_at_ms of the current epoch determines the due time. A client records `rotation_due` when due and prompts the mnemonic holder; ordinary writes MAY continue until rotation succeeds. The schedule is not an expiry deadline and MUST NOT strand an unattended chain. One participating device proposes reason scheduled via CAS; others see its commit and cancel their attempts. Mnemonic entry is still REQUIRED by §13.3. Unattended scheduled rotation without changing root-material rules is an unresolved capability, listed in Open Questions; implementations MUST NOT claim to provide it.

### 13.7 Fork and Rollback Detection

Persist the highest verified generation, parameters hash, epoch number/hash, log_id and prefix hash in protected local storage before advancing progress. Reject a lower generation/epoch or a different hash at a previously known position as `C_ROLLBACK_DETECTED`. Two valid different EpochRecords at the same epoch/predecessor, or divergent parameter descendants, are `C_EPOCH_FORK`. Stop new writes/enrollment/key erasure; retain both branches and obtain an independently authenticated head from another enrolled device or a mnemonic-holder session with a known export/checkpoint. Epoch links authenticate ancestry, not which branch an isolated client has never seen.

First-time recovery without a local pin or known peer requires explicit source selection (§11.6), then verifies the derived admin key and envelope commitments, but cannot know that the selected relay has hidden a later valid head. Peer enrollment pins the approver's checkpoint in the QR transcript. Relay log timestamps/sequence hashes alone are not a trusted global witness. A malicious relay can permanently isolate clients without presenting conflicting evidence; unconditional detection is impossible without an independent channel. Clients MUST state this limit, not manufacture an ordering from wall clocks. Signed membership at an epoch does not by itself prove when a malicious relay first accepted an old record (§18.4).

### 13.8 Mnemonic Compromise

Use a new mnemonic/passphrase and therefore a new chain/admin identity, read verified recoverable old state, convert it to freshly signed/encrypted records on the new chain, approve only fresh trusted device keys, verify completion, and separately retire/delete the old chain. Reusing the compromised mnemonic with new generation/epoch cannot remove root authority. Zeroizing a client's local copy cannot revoke an adversary's copy. The same-mnemonic 2.1 upgrade in §9 is not a remedy for mnemonic compromise.

## 14. Metadata Protection

### 14.1 Profiles

`private` is the genesis default and requires collection_tag null. `queryable` is explicit opt-in through signed policy; it exposes equality of a collection within an epoch. Every record remains padded and encrypted in both profiles. Policy changes require §17.5 re-seeding; old plaintext tags cannot be made secret retroactively. Neither profile hides chain/device relationships, timing, record counts or traffic sizes from the relay/network. Requests for narrower tagged data in queryable expose the requested tags to the relay as well.

### 14.2 Collection Tag

```text
collection_tag = b64u(HMAC-SHA256(collection_tag_key_n,
                    UTF8(NFC(InnerRecord.collection)))[0:16])
```

The input is the complete versioned collection identifier, without a terminator. The key is §5.3's key for that epoch. The receiver computes it after decryption and compares it to the signed envelope in constant time. A mismatch is `C_COLLECTION_TAG_MISMATCH`; private with a non-null tag or queryable with null is `C_SCHEMA_VIOLATION`. Do not expose names, operations, entity IDs, per-op counts or Lamports through HTTP headers/paths/extensions. Tags change when the epoch secret changes; the relay cannot calculate new tags, but timing and traffic can still correlate them.

### 14.3 Size Buckets and Framing

Record and snapshot part plaintext buckets in bytes are exactly `[1024,4096,16384,65536,262144,1048576]`. Let `P = UTF8(JCS(plaintext_object))`, `L = len(P)`. Choose the smallest bucket B such that `4 + L ≤ B`. Form `uint32_be(L) || P || CSPRNG(B - 4 - L)`, then encrypt. Empty padding is allowed. No compression is permitted; this avoids compression-oracle leaks and removes divergent size calculations. Oversized plaintext is split across records/parts; an individual oversized operation is rejected locally with `C_LOCAL_LIMIT`. The maximum encoded request still obeys §17.8.

Producers MUST preflight both operation count (1–1,024) and complete UTF-8 JCS InnerRecord size, including all envelope/operation/context/ext members, before encryption/signing and committing the immutable outbox record. The maximum JSON plaintext is 1,048,572 bytes; framed plaintext is at most 1,048,576 bytes and ciphertext at most 1,048,592 bytes (16-byte tag). The operation-count ceiling does not guarantee that a batch fits. Pack smaller batches with independent record IDs and valid author sequencing when either bound would be exceeded. If one operation plus its required InnerRecord envelope cannot fit, fail locally with C_LOCAL_LIMIT and retain the user's unsent intent; never truncate fields, split one operation semantically, or mutate a signed record while retaining its ID. Validate the encoded request separately against §17.8; server request-size overflow is PAYLOAD_TOO_LARGE, structural field-size violations use INVALID_FIELD. A receiver rejects malformed decrypted frame/schema as C_SCHEMA_VIOLATION and applies no subset of its operations.

After decryption require a standard bucket length, `1 ≤ L ≤ B-4`, parse exactly L bytes as valid JSON, and require those bytes equal JCS of the parsed object. Padding is arbitrary ignored bytes, not JSON whitespace or a signed `padding` member. Clients MUST NOT expose the unpadded length to the relay. Device metadata uses the same frame and buckets `[1024,4096]`. Snapshot plaintext uses §16.6's object, not InnerRecord, but encryption/signature/AAD use SyncRecord unchanged. `ciphertext` in EpochKeyEnvelope is always the raw secret plus tag and is not bucketed.

### 14.4 Batching and Queries

Batch operations from one collection to reduce per-action traffic, bounded by 1,024 operations and the largest bucket. A private client still uses null tags. Batch size is a scheduling choice, not a convergence rule. A deployment MAY add random transmission delay or fixed-time polling; it MUST NOT claim that padding alone hides traffic analysis. No plaintext search or entity-ID lookup API exists; local pagination and encrypted snapshots serve history UI. Tagged filtering returns ciphertext for a collection/epoch and cannot provide history sorting, unseen membership or plaintext counts.

## 15. Conflict Resolution

### 15.1 State and Total Comparison Key

For each ordinary entity store its maximum operation under:

```text
K = (lamport, op_rank, device_id, record_id, op_index)
op_rank(upsert) = 0; op_rank(delete) = 1; op_rank(clear) = 1
```

Compare lamport/op_rank/op_index as nonnegative integers; device_id/record_id by decoded 16-byte UUID unsigned lexicographic order. Collection/entity identifiers compare by NFC UTF-8 bytes only when an additional display/index tie-break is needed. K is unique for each operation in a valid log; same K with different content implies an invalid signed-object/ID equivocation. Rank one makes both delete and clear beat an upsert at equal Lamport, regardless of device/record bytes. Delete versus clear may tie at rank one; they affect different registers, and both suppress lower upserts. No relay sequence, timestamp, arrival order or local counter participates in K.

Logical state is the ordinary winning-register map, maximum clear register per declared scope, maximum retention-policy register per scope, device sequence evidence and Lamport maximum. Local cache membership, download progress, unsupported-schema state and presentation placeholders are not logical application state. Same validated log/snapshot plus suffix yields identical logical state and, given the same safety/policy projection, the same indexed live set.

### 15.2 Lamport Stamp

Persist `L` per chain/device. On receipt of any valid known operation set `L = max(L, op.lamport)`; never advance L for failed signatures/decryption. Before authoring each operation set `L = L+1` and assign it; stamp allocation and outbox construction are one transaction. Distinct offline devices can use the same Lamport. All operations in one new record increase strictly; multiple records MAY arrive out of order. A snapshot includes the observed maximum L, and new devices initialize at least to that maximum before writing. At `2^53−1`, stop authoring with `C_COUNTER_EXHAUSTED`; do not wrap/reset Lamport on epoch/generation changes. Recovery is a new chain with explicit state migration. An authenticated malicious member can jump L near exhaustion; no undocumented skew threshold may reject otherwise valid concurrent operations.

### 15.3 Tombstones and Clear Watermarks

Delete is a winning per-entity tombstone, not physical removal of conflict evidence. Clear updates only the maximum K for its explicit collection/scope; it does not enumerate every entity and does not clear other collections. For an entity e let `C(e)` be the maximum clear K across matching scopes (`all`, and seen/viewed as relevant), or bottom if none. The entity is live iff its winner is upsert and `winner.K > C(e)` and it is not excluded by an explicit user retention projection (§16.3). A later upsert above a delete/clear may resurrect it, which is the defined LWW behavior. Concurrent equal-Lamport upsert loses even if it arrives last. Tombstones/clear floors MUST survive snapshots/pruning; a tombstone may be dropped only when its rejecting floor and complete coverage are retained so that no older event can revive that entity (§16.7). No time-based tombstone GC is conformant by default.

### 15.4 Transition Algorithm

```text
apply(record):
    verify_complete_record_or_quarantine(record)
    if exact_record_id_and_hash_already_covered(record): return
    transaction:
        for i, op in enumerate(record.inner.operations):
            k = (op.lamport, rank(op.operation), record.device_id, record.record_id, i)
            L = max(L, op.lamport)
            if is_retention_policy(op):
                policy[collection, op.body.scope] = max_by_K(policy[…], (k, op.body))
            else if op.operation == "clear":
                clear[collection, op.context.scope] = max_by_K(clear[…], k)
            else:
                winner[collection, op.entity_id] = max_by_K(winner[…], (k, op))
        mark_exact_record_applied(record.record_id, object_hash(record))
        update_affected_disk_indexes_and_projection()
        commit

visible(e):
    w = winner[e]
    return w exists and w.operation == "upsert" and w.K > max_matching_clear(e)

merge(a, b):
    pointwise_max_K(a.winners, b.winners)
    pointwise_max_K(a.clear_registers, b.clear_registers)
    pointwise_max_K(a.policy_registers, b.policy_registers)
    union_exact_validated_identity_and_sequence_evidence()
    L = max(a.L, b.L)
    recompute_projection_from_the_merged_registers()
```

Bottom is less than every valid K; a missing register is bottom. A newer record containing some losing operations still advances the observed Lamport maximum and sequence evidence. Recompute floors from winners rather than eagerly deleting losers during arrival; otherwise delayed events and policy changes could yield different results. Authentication/eligibility is resolved before this algorithm, and identical validated input is the premise of convergence.

### 15.5 Fractional Order Keys

Favorite tags use finite strings over digits `0`–`9` and lowercase `a`–`f`, 1–256 characters, with the last digit nonzero. Interpret a key d as the exact rational `integer_hex(d)/16^len(d)` in `(0,1)`. This canonical representation (no trailing zero) makes exact rational order equal to ASCII lexicographic order. Endpoints 0 and 1 are virtual bounds, not valid keys. Allocate between a < b by finding the smallest n for which an integer m satisfies `a*16^n < m < b*16^n`; choose the smallest such m, encode exactly n hex digits including leading zeros, then remove trailing zeros. Use arbitrary-precision integer/rational arithmetic, never floats. If n exceeds 256, return `C_ORDER_KEY_EXHAUSTED`; preserve the current list and allow a user-confirmed reindex with new higher-Lamport upserts. Do not perform arrival-dependent automatic reindexing. Concurrent allocations can choose the same key; ascending K then entity_id provides deterministic display ties. The earliest user intent is not guaranteed under concurrent moves; convergence is.

### 15.6 History Order, last_access_seq and Eviction Floors

`last_access_seq` is a **derived full K of the winning upsert**, not a per-device integer or relay sequence. Store its five columns (or a lossless fixed-format tuple) in the local index. Descending K yields most-recent logical access first for search and viewed entities. Upsert to the same entity updates that row's K/body only when it wins; no array rewrite or delete-then-add is used. Equal Lamports use the remaining K fields, not created_at_ms. Seen membership needs no list order, but its winning K supplies deterministic cache priority.

A projection's `eviction_floor` is the lowest retained `(K, entity_id UTF-8 bytes)` when exactly N live entries fit a finite projection limit; it is bottom otherwise. Entries below it may be absent from that projection, but their authoritative registers/events remain in the cold store. Compute the top N over the **entire known live set**, not only the last-arriving page. The floor can move down when an entry is deleted or policy changes; it is not a monotonic deletion watermark. Only explicit deletes/clear are monotonic rejecting evidence. A snapshot records projection limit/floor separately from those registers so bootstrap cannot mistake local cache eviction for user deletion. §16 distinguishes explicit user retention projection from resource-safety projection.

### 15.7 Convergence Argument

The logical merge operation is pointwise max on a total order plus union of immutable identity/evidence sets; it is associative, commutative and idempotent. Visibility is a pure function of winners and scoped clear registers. Ordering and top-N projection are pure functions of those winners and the winning policy. Thus duplicate records, replayed operations and arbitrary arrival permutations converge. This does not guarantee convergence between different withheld prefixes, unverified snapshots, unknown extension schemas or malicious-device equivocation; those conditions are reported, not resolved by wall-clock fallback. Appendix D includes concrete executions.

## 16. Retention, Snapshots and Compaction

### 16.1 Defaults and Safety Ceilings

Search history, feed seen history and viewed history perform no automatic logical-history deletion by default. No routine timer/count truncation, age-based deletion, implicit clear or automatic synchronized tombstone is allowed. Entries are removed from logical visibility only by explicit user delete/clear or explicit user retention configuration. All chain data is a deletion target on authorized chain deletion. Immutable synchronization events remain stored unless the user explicitly authorizes compaction/pruning or a disclosed relay quota prevents further storage. The term "unlimited" in a null retention setting means no configured automatic deletion/projection-count policy; it is not a promise of infinite physical disk, free relay storage or perpetual availability. The named MAX_* constants are hard bounds on eager materialization, not hard bounds on the preserved logical archive. A count alone does not stop default writes. §16.4 is the authoritative behavior table for limit states, synchronization and snapshots.

| Scope | Constant | Safety ceiling |
|---|---|---|
| palleria.search_history/3 / all | `MAX_SEARCH_HISTORY` | 1,000,000 |
| palleria.view_history/3 / seen | `MAX_SYNCED_SEEN_ILLUSTS` | 10,000,000 |
| palleria.view_history/3 / viewed | `MAX_VIEW_HISTORY` | 1,000,000 |

These ceilings bound a client's eagerly maintained primary index. Beyond them, the client uses segmented cold indexes and top-N projection; it MUST preserve the event/state on disk and accept a newer entry by default, rather than delete old history or reject a write solely due to this count. The complete disk register map may exceed a safety ceiling; only bounded segments/pages are opened. A device unable to extend its disk/cold store reports `storage_blocked` and can stop local authoring. Relay capacity/quota or a configured user stop policy MAY stop writes (§16.4). The blind relay cannot enforce plaintext history counts in private or queryable mode.

### 16.2 In-Band User Policy

Default history limit is null (no configured finite projection limit) and stop_on_safety_limit false. A user explicitly changes a synchronized policy by an upsert with `entity_id:"*"`, `context:{"scope":"retention"}`, and body:

```json
{"scope":"all","limit":null,"stop_on_safety_limit":false}
```

`scope` is all only for search; seen or viewed only for view history. All fields REQUIRED. `limit` is null or integer 1 through that scope's safety ceiling; `stop_on_safety_limit` is boolean. These reserved operations update a separate LWW policy register by their normal K, not a history entity or clear register. Each view scope has an independent register; no `all` policy for view history is accepted. The policy is encrypted in the collection's ordinary record. Policy controls the default display/retained projection and write-stop preference, **not deletion of the immutable archive**. Clients MUST explain this before the user chooses a finite limit; actual erasure requires delete/clear and, for historical ciphertext removal, explicit pruning/deletion. Restoring null can show archived entries again. This avoids converting resource-safety eviction into irreversible deletion.

### 16.3 Deterministic Local Eviction

For each scope evaluate live winners after clear/tombstones, sort descending by `(K, entity_id UTF-8 bytes)`, and materialize the first min(user finite limit if any, safety ceiling). Archive remaining registers in a cursor-addressable cold index with their complete winning evidence. Track the computed eviction floor (§15.6), never emit deletion operations for this eviction, never destroy the only plaintext/ciphertext copy, and never use arrival time/created_at_ms/random LRU to select the replicated projection. A smaller device MAY cache fewer bodies as an additional local cache choice; it MUST label logical retention/counts, the synchronized projection and local cached/displayed ranges independently (§12.3). A smaller cache does not change the archive, policy register, winner/tombstone evidence or remote logical state. Deleted winners remain tombstones. An explicit upsert for a cold entry can bring it to the front through its new K. Late lower-K upserts cannot overwrite a newer winner; floors alone MUST NOT replace exact winner evidence for that test.

### 16.4 States, Codes, Display and Recovery

| Local state / server failure | Trigger | Client display and required recovery |
|---|---|---|
| `normal` | Scope count below ceiling, disk available. | No retention warning; default no automatic deletion. |
| `safety_limit_reached` / `C_SAFETY_LIMIT_REACHED` | Live scope count reaches/exceeds ceiling. | Nonfatal status: history remains preserved; recent index capped, older entries in archive. Continue writes by default, offer paged archive access/export. This is not corrupt-data quarantine. |
| `write_paused_by_policy` / `C_WRITE_PAUSED_BY_POLICY` | User stop_on_safety_limit true and a new distinct live entity would exceed ceiling. | Keep existing data and unsent intent; ask user to disable stop, explicitly delete/clear, or move/export. Upsert of an existing entity and deletes/clear remain allowed. A lower configured finite projection limit alone does not pause writes. |
| `quota_blocked` / HTTP 507 QUOTA_EXCEEDED | Relay max_bytes exhausted. | Preserve local outbox, show quota/used bytes from parameters; increase quota, explicitly compact/prune safely, or migrate relay. Do not retry indefinitely without change. |
| `storage_blocked` / C_LOCAL_STORAGE_FULL or HTTP 507 STORAGE_UNAVAILABLE | Client disk full or relay transient physical storage failure. | Pause writes needing storage; keep keys/checkpoint/outbox intact, free unrelated local cache, restore storage/relay or migrate. Retry with backoff only after capacity check; never discard history to hide the error. |

The table is the single normative source for all collection-ceiling effects. In safety_limit_reached, pulls, existing-entity upserts, new entities, snapshots and compaction remain allowed subject to actual disk/quota capacity; do not omit cold state or publish new tombstones. In write_paused_by_policy, only local creation of a new distinct live entity is paused; pulls, existing-entity upserts, delete/clear and complete snapshots remain allowed. Quota/storage failures may prevent persistence or publication but never make an incomplete snapshot sufficient for pruning/key expiry. Compaction reduces covered log storage only after full state handoff (§16.7); it does not erase live logical history or necessarily lower its entity count. Explicit delete/clear may lower the live count, while retained tombstones/evidence still consume disk. UI MUST distinguish live count, eager projection count, cold archive and available bytes; it MUST NOT label MAX_* as an archive storage cap.

Local write-stop decisions are not server validation rules and do not quarantine otherwise valid remote entries. Even if remote entries exceed a user stop preference, receive and index them in cold storage, and report the limit. A client must have capacity to persist an incoming chunk before advancing its cursor. Quota changes may resume the same signed outbox with fresh tokens, unless an epoch/generation change requires §11.1 rebuild.

### 16.5 Large-History Operation

Clients MUST NOT read all history into memory. Initial history UI fetch is 100–500 rows from the local keyset index; subsequent pages use full tuple cursors pinned to an index revision, or restart pagination after a concurrent reorder. Seen membership uses an indexed entity lookup with minimal body. Viewed detail bodies can be lazy; keep existence/K/index available independently. On-disk segmented manifests/indexes and bounded worker transactions permit millions of entries. The protocol guarantees deterministic state on complete input, not an O(1) full bootstrap or a complete local answer before required input is received. Show partial/unknown membership during incomplete bootstrap; do not silently treat unknown as unseen. Sync can pause/restart and displays §11.2's progress.

### 16.6 Snapshot Store and Bootstrap

A snapshot is a lossless representation of a fully verified prefix's logical state, including **all hot and cold histories**, winning tombstones, matching clear registers, retention-policy registers, observed Lamport maximum, and author device_seq/predecessor evidence. It is not the last 100 displayed rows and not a bag of current visible values. The separate store encrypts it using signed SyncRecord parts with current-epoch keys and §7.2 AAD. Part record plaintext replaces InnerRecord with the following REQUIRED members:

```json
{"type":"PALLASYNC-SNAPSHOT-v3","collection":"pallasync.snapshot/3","compaction_id":"<uuid4>","part_index":0,"part_count":1,"entries":[]}
```

`collection` is exactly the reserved snapshot-format identifier `pallasync.snapshot/3`; it is not an Operation collection and is forbidden on the ordinary event endpoint. In queryable profile its tag is computed by §14.2 from this string; in private the tag is null. `part_index` is 0-based, part_count 1–65,536, entries a bounded array. Each entry is exactly one of:

| entry.kind | Required members in addition to kind |
|---|---|
| `header` (exactly one, first) | `chain_id, generation, log_id, covered_through_seq, covered_log_hash, epoch_hash, lamport_max` with types from §7.8/§15.2. |
| `entity` | `collection:string, entity_id:string, key:K-array, operation:"upsert"\|"delete", body:object, context:object` using original schema validation; delete body/context empty. |
| `clear` | `collection:string, scope:enum, key:K-array`. |
| `retention` | `collection:string, scope:enum, key:K-array, limit:integer\|null, stop_on_safety_limit:boolean`. |
| `author` | `generation:uint32, device_id:uuid4, device_seq:counter, record_hash:b64u(32)` for the highest observed valid authored record. |
| `author_gap` | `generation:uint32, device_id:uuid4, first:counter, last:counter` with first ≤ last; disjoint missing authored ranges. |
| `projection` | `collection:string, scope:enum, limit:integer, eviction_floor:object\|null`; non-null floor exactly `{key:K-array,entity_id:string}`. |

K-array is `[lamport,op_rank,device_id,record_id,op_index]`; op_index 0–1023, rank 0 or 1. Schema/UUID/counter validation is unchanged. Header generation/log/prefix values match CompactionRecord. Snapshot author evidence preserves the highest observed author head and unresolved authored gaps as author_gap entries. It MUST NOT claim those authored gaps are resolved; this does not block verification of a contiguous available relay prefix when each of its accepted entries is validated. A missing relay entry, invalid object or unproven acceptance does block that prefix. Registry/epoch signed histories remain separate required bootstrap evidence. Entity records retain even clear-suppressed winners unless an exact equivalent rejecting floor plus coverage permits removal. `projection` entries do not define logical existence.

Canonical entry order: header, then entity, clear, retention, author, author_gap, projection; within each kind sort lexicographically by its identity tuple encoded as UTF-8 strings with integer generation numeric (entities: collection, entity_id; clear/retention/projection: collection, scope; authors: generation, device_id UUID bytes; author_gap: generation, device_id UUID bytes, first numerically). Reject duplicate identities or multiple headers. Partition this single ordered stream into parts without splitting an entry, using §14.3 size limits; parts' part_index and listed record hashes must match the CompactionRecord. Canonical state bytes are the literal ASCII `[` followed by comma-separated JCS entry bytes in that order followed by `]`, independent of part boundaries. Stream the HMAC with the snapshot epoch's record_key over these bytes; this is `state_sha256` (§14.5). Do not hash a displayed subset. A large entry must fit one part; failure is `C_LOCAL_LIMIT`. If complete state would exceed 65,536 parts, abort complete-snapshot publication with C_LOCAL_LIMIT, retain/replay the full required log and state/evidence, and do not authorize pruning or old-key expiry that depends on a nonexistent complete handoff. Never split coverage into incomplete snapshots and call one a complete bootstrap; ext, new collection names and operator settings cannot increase this 3.x ceiling. Future larger representations require the separate version decision in §0/OQ-05.

Bootstrap: pass applicable policy consent and §11.6 initial-source selection, authenticate parameters/admin identity and full epoch/registry history; select a snapshot anchored to a trusted checkpoint or verified author; fetch/verify each part signature/hash/AAD/commitment/frame; validate/order all entries and streaming state commitment; atomically install in a staging database; establish covered prefix hash/sequence and Lamport; apply the log suffix above covered_through_seq with its chain/hash continuity; then publish the database and advance the verified cursor. Interrupted downloads leave only staging state and resume by part hash. Never partially replace the live DB. Unknown/untrusted snapshot authors require full replay/recomputation or explicit user trust of the authenticated authorized source/author selected under §11.6; an Ed25519 signature alone cannot prove a snapshot omitted no entities. For a priority bootstrap the UI can publish verified partial indexes with a visible partial flag, but cannot advertise full prefix verification before all state is checked.

### 16.7 Compaction and Post-Pruning Verification

Compaction preserves application state; pruning removes raw events and is separately admin-authorized. Before pruning ensure the latest snapshot is complete, current-key decryptable under the selected retention profile, covers the entire pruned prefix, and its source state was fully verified. Retain signed ChainParameters history, enrollment/approval/revocation and epoch/envelope evidence needed for every retained author, CompactionRecord, snapshot parts, prefix boundary hash/sequence, author heads, exact duplicate-ID/hash evidence for removed records, tombstones/clear/policy registers and deletion ledger. Removed record identity evidence prevents a reused ID or old replay becoming a new operation; it may be an exact disk table, not a probabilistic filter.

If an unsupported collection prevents constructing complete state, retain its exact records and necessary keys; do not prune or expire the covering prefix until its schema is implemented or an explicit verified-state migration documents the exclusion. Unsupported ciphertext cannot be treated as an empty collection merely to obtain a compact snapshot.

The first suffix entry is `covered_through_seq+1`; recompute §17.3's prefix hash from the retained boundary. Validate its author/epoch using historical evidence, then compare the final prefix with a pinned/advertised head. Previously covered identical records cause no state change; conflicting IDs quarantine. A mismatch, missing required evidence, incomplete history state or changed log_id stops bootstrap/pruning. A new client without a preexisting checkpoint necessarily trusts an authenticated snapshot author for semantic completeness, or requires an independently retained full export; this trust limit cannot be removed by hashing the snapshot itself. After pruning, clients MUST NOT claim they can reconstruct raw event bodies that no longer exist, although the complete materialized histories remain available.

## 17. Relay Operations

### 17.1 Durability Tiers and Transport

TLS 1.2 or later is REQUIRED. TLS 1.3 is RECOMMENDED; older TLS gives deployments fewer modern transport protections but does not change v3 object validation. Relays MUST advertise exactly one durability tier:

| durability_tier | Meaning of accepted commit | Stated failure boundary |
|---|---|---|
| `single-durable` | Committed transaction and its write-ahead log fsynced on persistent storage. | Survives process/reboot; host/disk/site failure may lose data. |
| `replicated-durable` | The durable transaction acknowledged by at least two independent storage failure domains. | Survives one such domain loss; correlated failure remains possible. |
| `backup-durable` | Replicated-durable plus encrypted off-site backups at least daily, restore tested at least every 90 days. | A restore may roll back up to the disclosed backup interval; clients detect/repair. |

Memory-only acceptance is not a conformant tier. “Backup-durable” is not zero data loss. Export the tier, backup interval and last successful restore test in operator documentation; health exposes the tier only. Relays MUST disclose max_bytes quotas and backup expiry/deletion policy before genesis. An operator may promise stronger durability but cannot weaken the meaning of an accepted record. Operator-specific privacy.md is REQUIRED (§17.12); no universal storage quota, actual backup interval/retention period or operator copy lifetime is assigned by this protocol. Tier minima above remain binding. Deployments MUST state actual values or an explicit inapplicable/disabled condition before client consent/use (§11.7), never leave these deployment decisions undecided in a live policy.

### 17.2 Acceptance, Sequencing and Backup

Accepted means the entire signed object, unique-ID index, log receipt, replay/idempotency outcome and all relevant head/registry updates are durably committed before the HTTP response. Per-chain `relay_seq` increments exactly one per new LogEntry, never reuses an issued value under the same log_id, and is not embedded in a SyncRecord. Genesis log order is parameters, creator device, envelopes sorted by recipient kind (`device` before `recovery`) and recipient_device_id, epoch. For an epoch transaction: newly staged devices sorted by ID, envelopes in that same order, optional admin operation, then epoch; the epoch's commit makes the complete bundle visible atomically. Subsequent standalone devices/envelopes/compactions/admin actions are independent entries. Re-seed uses the same ordering and its final compaction. Identical accepted retries append no entry.

Backups MUST preserve signed values, parameters/epoch/registry histories, sequences, log_id, prefix hashes, snapshot stores, deletion ledger and replay cache or the §6.3 restart rule. Backups store only ciphertext and relay operational data; the relay never has record or recovery keys. Encrypt operator backups under an operator-controlled key, distinct from PallaSync E2EE keys. Restore into staging, verify structural/hash consistency and deletion ledger, and reject resurrection of ledger-deleted chains. A stale backup lacking the current deletion ledger MUST NOT be exposed before ledger reconciliation.

### 17.3 log_id, Prefix Verification, Withholding and Repair

`log_id` is a random UUIDv4 identifying a relay log incarnation. New genesis assigns one. A healthy restart preserving all accepted data/sequence history retains it. Restore that may have lost previously acknowledged entries, or migration to an independently reseeded relay, MUST allocate a new log_id before serving; clients then invalidate old relay cursors and perform checkpoint reconciliation. An operator cannot claim unchanged identity after known sequence loss. Sequence numbers may restart in a new log_id; generation does not change just because a backup was restored. Old `(log_id, seq)` receipts remain evidence. A malicious relay can lie about incarnation; pinned prefix/head hashes still constrain previously observed views.

Define H0 = SHA-256(ASCII(`PALLASYNC-LOG-v3\0`) || decoded chain_id || decoded log_id UUID bytes). For each ascending entry i, `H_i = SHA-256(H_(i-1) || uint64_be(i) || SHA-256(JCS(LogEntry_i)))`. `head_hash`/`covered_log_hash` are b64u of this digest. Integers remain ≤2^53−1 even though encoded in 8 bytes. A suffix after pruning starts from its stored signed-compaction boundary. LogEntry includes all response fields defined in §10.9, including commit time when present; the relay MUST preserve them across reads/backups. A dishonest relay can compute a fresh self-consistent prefix, but cannot alter a prefix pinned by a client or covered by a trusted signature without detection. Unsigned head advertisements alone prove no completeness.

Per-device encrypted device_seq and prev_record_hash identify missing or conflicting authored records once a later record or checkpoint is observed. Store gaps and request repair/source export. Withholding the last record or an entire device's tail is undetectable absent independent checkpoint exchange; a filtered pull cannot prove no missing records. A record sequence gap is not automatically a fork. Repair upload under A accepts only records with verified historical acceptance/authority evidence, preserves their record_id/signature, and associates new log receipts with source receipts. It cannot create a new accepted history for a revoked signer just from an old valid signature. If verification fails or original prefix is unavailable, use verified-state re-seeding rather than inventing acceptance times.

### 17.4 Export Format

Export is UTF-8 JSON Lines, one complete §3-valid JCS object per line, LF separated, no blank lines. Each HTTP chunk starts with one header and ends with one continuation marker. The client combines chunks, removes repeated header/continuation lines when constructing a single archive, then writes one final footer. The core header example below additionally requires the attestation metadata in §17.10; placeholders denote types, not literal wire-valid identifiers. The complete header field set is this example plus relay_public_key,relay_key_id,transparency_id,transparency_head_index,transparency_head_hash. A core header example is:

```json
{"kind":"header","protocol":"pallasync/3","chain_id":"<chain_id>","generation":0,"log_id":"<uuid4>","head_seq":100,"head_hash":"<b64u32>","include_recovery":false}
```

Primary data lines are exactly `{kind:"log",entry:LogEntry}`, `{kind:"snapshot_part",record:SyncRecord}`, or `{kind:"compaction",compaction:CompactionRecord}`; attestation evidence lines/header additions are REQUIRED as specified in §17.10. Headers, retained prefix boundaries, parameter/registry/epoch histories and exact removed-ID evidence are required for a complete export; special evidence lines are `{kind:"boundary",compaction:CompactionRecord}`, `{kind:"removed_id",record_id:uuid4,record_hash:b64u(32)}`, and `{kind:"source_receipt",receipt:LogEntry}` when repair has changed log_id. Control objects with no retained current-log entry are `{kind:"control",object_type:"parameters"|"device"|"epoch"|"envelope"|"admin",object:signed object}`. Log lines are in relay_seq order; remaining groups are sorted by kind then object ID/hash. Recovery envelope objects/entries are emitted only for A with include_recovery true. A D export omits recovery ciphertext, marks include_recovery false, and is not a mnemonic-only complete archive; omitted sequence positions are indicated by `{kind:"omitted",relay_seq:seq,object_hash:b64u(32),reason:"recovery_authority"}`. Such positions cannot be independently recomputed as the full prefix, and the exporter MUST label that limitation.

Chunk trailer: `{kind:"continuation",next_cursor:string|null,has_more:boolean}`. Final archive footer: `{kind:"footer",line_count:integer,archive_sha256:b64u(32),complete:boolean}`; hash covers exactly all preceding archive bytes including LF, excluding the footer. The footer is created and verified locally for a downloaded archive; it is an integrity checksum, not relay authenticity. `complete:true` means all source objects/evidence through the pinned head and all referenced parts are included, and include_recovery true if recovery completeness is claimed. Export/resume cursors pin the head; uploads after it require a separate suffix export. Verify archive hashes and all signatures/AEAD before migration/restore. Do not mix plaintext exports or mnemonics into this format. Exports contain ciphertext and metadata and must be protected because a mnemonic holder can decrypt retained recovery material.

### 17.5 Re-seeding Through generation

Re-seeding reconstructs a chain from verified state after relay loss/migration; it is not an epoch rollback, revocation bypass or deletion undo. Only A may commit it. Obtain the latest authenticated parameters/epoch checkpoint and a complete snapshot/export; stop if competing heads cannot be resolved. Create parameters with generation+1 and previous_parameters_hash; retain the same chain_id/admin_public_key. Enroll fresh random device IDs/keys with certificates for that generation, and create the next global epoch with reason reseed, fresh secret and complete recovery/device envelopes. Old-generation devices cannot upload into the new generation. Import complete application registers, tombstones, clear/policy floors and Lamport maximum without resetting their original K, and re-encrypt the state in current-generation snapshot parts. K's device IDs remain historical references, not new membership grants.

Before re-seeding, A submits the original signed parameter/epoch/registry control history to `POST /chains/import` (A verified against its supplied original parameters), body `{parameters_history:ChainParameters[],epoch_history:EpochRecord[],device_history:DeviceRecord[],envelopes:EpochKeyEnvelope[],compactions:CompactionRecord[]}`. This route is part of the §10.3 administrative restore API and permits no query. Each history array is ordered by generation/epoch or enrollment evidence; arrays may be empty only where no such object exists. Request-size limits still apply; a source requiring more than one request stages consistent consecutive chunks with the same last parameters/epoch head and receives the same staged log_id. This is staging only: `202` `{chain_id,state:"staged",log_id:uuid4}`; history/ledger conflicts return `409 IMPORT_CONFLICT` / `410 CHAIN_DELETED`. It stores no new writable head or unapproved member. Repeating the exact staging history is idempotent. For an existing relay the old chain stays live until commit; import allocates a replacement incarnation without changing it. For a replacement relay no ordinary chain is readable/writable before commit. Snapshot parts may then be staged under A. For proposed generation+1 parts, A staging validates structure/hash and holds them untrusted until PUT parameters supplies the new DeviceRecords/epoch to verify their signatures and bindings; these parts MUST NOT be exposed as valid snapshots beforehand. PUT parameters commits the next generation and complete snapshot atomically. Historical K/evidence remains available for validation, and the new CompactionRecord is signed by one of the fresh devices in the REQUIRED nonempty `device_records` array. Its AdminOperation payload hash includes that array. CAS still refers to the live/imported original heads, not the staging placeholder.

For re-seed snapshot construction, the new log_id and boundary H0 are returned by the staging import; coverage is sequence 0 in that new incarnation, while original verified application state and source receipt evidence are retained. Compaction's generation/epoch hashes name the staged new state. A relay MUST NOT interpret coverage 0 as permission to discard imported source verification evidence. Failed staging can be retried idempotently; a failed commit leaves a live existing chain unchanged and a replacement chain staged/unavailable. Clients verify the full new parameter ancestry, epoch ancestry and admin operation, replace cursors after install, preserve unaccepted edits for rebasing above imported Lamport, and explicitly approve fresh enrollment. A relay must refuse reuse of the same deterministic chain_id after authenticated deletion; a new mnemonic is required for a new chain.

At re-seed commit (§17.5), all previous-generation non-revoked registered device IDs are retired to revoked state and named in the new EpochRecord's revoked_device_ids; they are disjoint from fresh members. Old certificates remain historical evidence, never current token authority. A token naming a DeviceRecord from a different generation gets GENERATION_MISMATCH even if its historical wrapper once said active. Fresh subjects acknowledge the committed key under §10.8; a staged re-seed snapshot author is allowed only by the enclosing AdminOperation's approval and does not bypass ordinary endpoint membership rules.

### 17.6 Relay Migration and Shutdown

Relays do not federate or silently synchronize each other's registries. Migration: authenticate source head, create an A export/verified snapshot, verify source completeness, stage target/import, commit generation+1 as §17.5, bootstrap/verify at least one target client, then update the user-selected relay origin and resume enrollment/writes. Mint tokens with target aud. Freeze source writes at cutover; if source cannot be frozen, pause clients and perform a final verified suffix capture. Any old-generation write racing after cutover remains on source only and is reported as an unimported edit, never silently replicated. Do not keep two independently writable heads under one generation.

A planned shutdown MUST advertise relay-notice at least 30 days ahead where operationally possible, retain authenticated exports until the announced time, and document quota/deletion consequences. Sudden failure may make this impossible and is an availability limit. `migration_origin` is a suggestion requiring explicit origin selection/checkpoint validation; it grants no authority to a new relay. Shutdown uses `503 RELAY_SHUTTING_DOWN` after writes stop, optionally with Retry-After and notice context, never 410. Source deletion after a successful migration is a separate authorized deletion action; a target MUST reconcile deletion-ledger scope. A deletion of the logical chain is chain-wide, whereas retirement of an obsolete relay copy must use operator copy-retirement procedures and MUST NOT publish a chain-deletion tombstone to the target. No v3 API purports to erase an operator copy without logical chain deletion.

Migration origin validation is a mandatory guard: `migration_origin` and relay-notice are suggestions only. A client MUST obtain explicit user selection of the destination before contacting it for chain operations, minting destination tokens or sending any export/history/ciphertext. Display the normalized HTTPS origin, authenticate TLS, require health.relay_origin exactly equals the selected origin and each new token's aud, establish/verify the separate relay key pin, and verify known chain_id/admin identity, complete parameter/epoch/registry ancestry and source pinned prefix before cutover. An initial target staging log does not share source log_id: validate source evidence and authorized generation+1 continuity, not numeric head equality. No cross-origin Authorization forwarding, automatic redirect following with a token, origin replacement, key erasure, copy deletion or root operation is permitted from a notice. Failure retains source/local state and requires explicit verified reconciliation. A candidate whose history contradicts known pins is refused even if its TLS/relay signature is valid.

### 17.7 Deletion Assurance and Ledger

Chain deletion makes all chain payload records, historical ciphertexts, snapshot parts, envelopes, device metadata and auxiliary ciphertext backups deletion targets. A relay first persists the deletion ledger entry, rejects subsequent chain writes, disables exports, then erases active stores and executes its disclosed backup process. The minimum ledger contains `chain_id,deletion_id,authorized_parameters_hash,authorized_epoch_hash,authorization_hash,requested_at_ms,completed_at_ms:ms|null,assurance,delete_after_ms:ms|null,receipt_hash`, all REQUIRED with these exact types (IDs/hash types as elsewhere). `authorization_hash` is the AdminOperation hash or hash of the authorized device Capability Token plus deletion request, held as protected audit evidence; the token is not published. `receipt_hash` hashes the JCS ledger object excluding that member. Ledger signed/admin evidence is retained to prevent resurrection, including after backup restore; it contains no decryption keys or user payload.

| Assurance | Claimed action | Limit |
|---|---|---|
| `crypto-shred` | Operator encrypts every chain's relay-storage/backup ciphertext under a distinct operator storage key and destroys every copy of that key, including backup/KMS versions, then removes active objects. | This key is separate from E2EE keys; claim invalid if plaintext ciphertext copies escaped that layer. Cannot erase user/device copies or prove malicious operator compliance. |
| `backup-expiry` | Active objects removed, backups prevented from restore/use by ledger and expire no later than disclosed delete_after_ms. | Data persists until expiry; completed_at_ms remains null until expiry/erasure checks complete. |

The relay cannot crypto-shred the users' E2EE epoch secrets it never possessed; operator storage-key destruction is the basis for that assurance level. Device-local deletion removes its wrapped keys, DB, caches and outbox when authenticated deletion is confirmed. A bare/unverified 410 response or unsigned deletion notification is not sufficient: verify the ledger authorization against pinned parameters/epoch authority (or the locally initiated authorized deletion) before erasing. If authorization proof is unavailable, suspend and show deletion_unverified, retaining local recoverable data. GET deletion returns `{ledger:object,parameters:ChainParameters,epoch:EpochRecord,enrollment_chain:EnrollmentCertificate[],admin_operation:AdminOperation|null,device_authorization:object|null}`. The relay retains these public signed authorization proofs alongside the minimal ledger, excluding encrypted device metadata and payloads. It retains the admin public key and, for a device deletion, its certified signing key to authenticate post-deletion GET requests. `device_authorization` contains the original decoded CapabilityToken and `{deletion_id,expected_parameters_hash,expected_epoch_hash,admin_operation:null}` request for permitted device deletion; exactly one authority form is present. Verify the token/body digest historically without treating it as a fresh reusable token, verify the parameter/epoch hashes against the ledger and pinned heads, verify policy and enrollment-chain signatures at deletion, and derive/check admin identity for mnemonic recovery. Device-authorized deletion with unproven historical active status or a head incompatible with a known later checkpoint remains C_DELETION_UNVERIFIED until independent evidence resolves it. A relay promise/checksum is not cryptographic proof of physical deletion. Expired backups must still preserve the minimal ledger separately.

### 17.8 Limits, Quotas, 429 and Backoff

| Limit | Base protocol bound / relay default |
|---|---|
| Raw JSON request / response | 8 MiB maximum each; export HTTP chunks also bounded. |
| Single plaintext/ciphertext record | Largest bucket 1 MiB / 1 MiB+16 decoded ciphertext. |
| Upload batch | 64 records; request byte ceiling may require fewer. |
| Operations per InnerRecord | 1–1,024. |
| Active plus pending devices | 128 maximum; retained revoked verification history does not consume an active slot. |
| Device envelopes per submission | 128; a complete epoch bundle includes up to 128 device envelopes plus one recovery envelope. |
| Snapshot parts | 65,536 maximum per snapshot; default chunk fits one standard record bucket. |
| Log/page limit | Default 200, maximum 1000, further reduced by byte ceiling. |
| Authorized requests | Default 120/minute per `(chain_id, signer)`; token-bucket burst 30. |
| Record uploads | Default 30 requests/minute per active device; burst 10. |
| Unauthenticated enrollment requests | Default 6/minute per source IP and 3/minute per offer; burst 3 and 1 respectively. |
| Concurrent exports / snapshot downloads | Default 2 per chain. |
| Storage max_bytes | Operator-declared integer or null; no protocol default quota and no implicit deletion. |

Hard wire ceilings cannot be increased within 3.x. Lower operator request/rate/storage quotas MAY be advertised before enrollment; health limits MUST reflect them so conformant clients adapt their batches. A rate limit is not an authorization to drop accepted data. `429 RATE_LIMITED` has `Retry-After` integer seconds 1–3600 plus context `{retry_after_ms:integer,scope:string}`; other rate limits may be tighter but must be disclosed. Retry-After is a minimum wait. For network failure/408/429/500/502/503/504, use capped exponential full jitter (500 first requires status/idempotency reconciliation): attempt a starting at 0, `base_a = min(60000,1000*2^min(a,16))`, wait random integer 0–base_a ms, then max with Retry-After if supplied. Persist next retry time; reset attempt after successful progress. Never block the UI thread or spin when the app is backgrounded. 401 clock failures follow §6.3; 403 and semantic 409 require lifecycle/reconciliation; 507 quota requires capacity change. Fresh token per retry, unchanged signed object for idempotent replay. No retry logic erases keys or creates a chain automatically.

### 17.9 Attestation Key, Receipts and Independent Checkpoints

The relay MUST generate/protect an independent Ed25519 attestation key and advertise `relay_public_key:b64u(32),relay_key_id:b64u(32)` in GET /health. The chosen HTTPS origin and key are pinned together at explicit user selection, with optional independently obtained key fingerprint. Initial TLS/key pinning is trust establishment, not proof of an honest operator. A different key at a pinned origin suspends attestations as C_RELAY_KEY_MISMATCH; require explicit operator/user verification and preserve old-key evidence. This Draft defines no automatic attestation-key rotation certificate: planned replacement requires explicit new trust establishment/reconciliation and a new transparency_id. Retained old receipts verify under their original pinned key. A relay key is never a chain admin/member key, recovery key or record decryptor.

Acceptance transactions MUST commit UploadReceipt and accept transparency entry atomically with the existing immutable data-log objects/head. Receipt/head signing failure means no accepted response; a committed transaction is retried by exact object lookup and returns the same receipt. For multi-object transactions, all receipts and transparency entries are committed together; expose the bundle only after final commit. One log receipt proves one object at its seq; a null-sequence snapshot receipt attests only its protected store acceptance; it does not assert the transaction's final head equals that object's resulting_head_hash. Client retains immutable receipt before dropping accepted outbox retry state and verifies the signature, object/entry hash recurrence, transparency reference and known pins. A signed receipt alone cannot justify resetting a newer checkpoint or treating an unobserved maliciously backdated record as accepted while active (§18.4).

Clients keep protected checkpoints `(origin,relay_key_id,chain_id,log_id,seq,H_seq,parameters_hash,epoch_hash,transparency_id,index,T_index)`, original receipts and observed contradictory signed heads. Periodic probes (§11.5) compare them. Existing local checkpoints and independent user-owned devices/export copies form the base independent comparison path; exchange signed DeviceCheckpoint (§7.12.4) and pin the peer's known certified key or establish independent user trust before comparison. Exchange public checkpoint/receipt evidence only, no shares/root keys. Offline public evidence can be kept apart from recovery media; signatures survive loss of the relay.

Hash-chained transparency is not a Merkle tree: verifying a new suffix or inclusion against a head requires every intermediate signed entry, streamed in bounded pages. A receipt's referenced entry plus a signed later head without the linking suffix is **pending proof**, not a verified inclusion. Recompute Ti, entry signatures and all indexes, compare at an already pinned anchor or explicitly accepted initial T0, then verify the signed target head. Independently pin/exchange the resulting checkpoint. Huge suffixes cost O(entries); cancellation/resume stores public verified checkpoints, not unverified forward progress. Missing pages/proofs suspend the completeness claim; contradictions are C_TRANSPARENCY_INVALID.

A malicious relay can sign mutually inconsistent branches or hide a complete tail from an isolated client. Independent checkpoint comparison exposes contradictions once views meet, not every unseen omission. This limit also applies to [Certificate Transparency's split-view problem](https://www.rfc-editor.org/rfc/rfc9162#section-1); this specification defines its own linear hash chain, not the RFC's Merkle-tree wire protocol. Third-party public proof services, relay federation and automatically trusted mirrors are not enabled here: publishing chain ID/entry/hash/timing metadata is not automatically anonymous. An external witness/mirror requires explicit privacy/trust/transport design (Open Question OQ-06); clients MAY compare user-provided independently authenticated evidence without minting third-party relay tokens.

### 17.10 Transparency Persistence, Export and Restore

Transparency records accept/reject/prune/delete/migrate metadata only (§7.12.2), never payload plaintext, authentication tokens, user IDs, recovery pieces/blob or network-identifying logs. Entries reveal control timing/outcomes/object equality even with private metadata; chain-scoped authenticated access and no public enumeration are REQUIRED. They are operational evidence and not pallasync.audit/3. Do not upload local recovery events/artifacts as transparency objects.

Backups MUST preserve transparency entries, all published signed heads needed for pinned-prefix reconciliation, receipts and relay key protection independently of deletable ciphertext. Normal pruning removes no transparency entry/receipt. If storage policy cannot retain required attestations, advertise capacity exhaustion and refuse new commits; do not silently prune acknowledged evidence. Reject spam by authenticated rate/quota enforcement before candidate processing. Mutations after restoring a lost suffix must use fresh log_id/transparency_id and explicit evidence reconciliation; restored ledgers override obsolete writable state (§17.7). Old signed receipts remain evidence of loss, never evidence that the restore erased previously acknowledged objects.

Export §17.4 additionally emits `{kind:"upload_receipt",receipt:UploadReceipt}`, `{kind:"transparency_entry",entry:RelayTransparencyEntry}` and `{kind:"transparency_head",head:RelayTransparencyHead}` lines. The export header additionally has REQUIRED `relay_public_key:b64u(32),relay_key_id:b64u(32),transparency_id:uuid4,transparency_head_index:integer,transparency_head_hash:b64u(32)` for its pinned high-water view; all are checked against its signed exported head. Groups follow existing groups, sorted by non-null receipt relay_seq followed by null-sequence snapshot receipt_id / transparency index; head matches the export's pinned data head and transparency cut. Cursor pins both cuts in an atomic source snapshot; later reject/notice entries do not mutate that export. Footer archive hash covers the new lines. Complete attestation export includes the linking history from T0 or a separately trusted pinned boundary and every available receipt through the pinned data head. A partial/filtered export labels its attestation coverage and cannot claim independent complete-prefix verification. Recovery artifacts are still excluded; epoch recovery envelopes remain governed by include_recovery.

Migration/re-seed import keeps original relay attestations as source evidence in its protected administrative archive; they are not new signed control/application objects and do not grant target authority. Existing §10.3 import JSON remains unchanged. A target receives ordinary history under that route and source evidence via the verified administrative export workflow, issues its own fresh receipts for new accepted log entries, and does not sign forged source receipts. Target/source checkpoint/hash differences are reconciled through §17.5, not by comparing numeric sequences across log IDs. Federation/multi-writable mirroring remains outside this protocol.

### 17.11 Signed Deletion Evidence and Anti-Resurrection

GET C/deletion adds `{delete_receipt:DeleteReceipt,deletion_transparency_entry:RelayTransparencyEntry}` to its existing proof wrapper. DELETE's original request shape and authorization remain unchanged; 202 adds delete_receipt to its original response. The relay signs a receipt without witnesses. Users/authorized devices collect separately signed DeletionWitness objects through explicitly authenticated local exchange after the exact receipt is available, and retain DeletionEvidenceBundle (§7.12.5) beside that unchanged receipt. Bundle fields and every witness bind the complete receipt hash, not merely deletion_id. There is no relay-side witness intake and no witness addition to the DELETE body/token, ledger authorization hash or signed receipt. Witnesses confirm intent/observation; ordinary verified admin or policy-permitted device deletion authorization remains sufficient.

Verify ledger existence, deletion_id, receipt_hash recurrence, authorization hash/form, authorized parameter/epoch hashes and ancestry against pinned heads, enrollment/policy/CAS validity, relay key signature and matching delete transparency entry; verify optional witnesses separately. An incompatible later known head remains C_DELETION_UNVERIFIED; a relay-signed ledger alone does not supply admin/device authority or overwrite a newer pin. Unverified 410/unsigned notice/proof failure always enters deletion_unverified, suspends sync/writes/destructive automation and retains local keys, recovery packages, data and pending edits. Do not trigger another origin, clear a pin or accept resurrection as error recovery.

Before confirmed user-initiated deletion completes local erasure, retain the minimal signed public deletion evidence on at least one user-selected offline evidence medium or independently trusted existing device/relay archive; the client MUST offer/export it and report if no independent copy is available. A fresh target relay is not contacted automatically for this purpose. Never place root keys/shares or application plaintext in the evidence archive. Recipients of already verified deletion may erase locally without waiting for unreachable peers; independent-copy failure is disclosed, not an excuse to reactivate the chain. Post-deletion direct-mnemonic recovery can read the authorized ledger via GET C/deletion but cannot restore an erased logical chain. The relay preserves the minimal ledger, authority proofs, final delete entry/receipt and applicable relay verification key across every restore; full auxiliary history may be reduced after logical deletion to that minimal anti-resurrection evidence. Optional witnesses prove confirmation of intent, and operator crypto-shred/completion signatures prove claims, never physical erasure of all copies.

### 17.12 Mandatory Operator privacy.md

Each relay operator MUST publish an operator-specific public UTF-8 Markdown policy at `${relay_origin}/privacy.md` and mandatory signed RelayPrivacyDisclosure at `${relay_origin}/privacy.json` (§7.13) before allowing use. Machine-readable fields/schema permit deterministic presence/type/range/signature/cross-value checks; they do not prove actual operator behavior. Both resources are public and use the same disclosure/consent guards. The required disclosure content is specified in [privacy.md](./privacy.md), which is a normative requirements document, not a populated deployment policy. This public documentation resource is outside the authenticated REST API and receives no Capability Token, chain/device ID, account/Cookie or recovery material. Require HTTPS at the user-selected origin, 200 text/markdown;charset=utf-8 and a decoded-body ceiling of 1 MiB; same-origin conditional 304 requires the client's exact valid cached body. Cross-origin redirects/unavailable documents cannot silently supply terms for the selected relay. Clients enforce §11.7 before each chain request.

The operator-specific document MUST identify the operator/contact, applicable origins, revision/publication/effective dates, change notice/archive process; actual quota/rate scope/values/counting/capacity behavior; exactly one accurate durability tier; backup presence, maximum interval/retention/expiry/restore-test process; every operator copy class (active/replica/WAL/backup/staging/cache/export/support/log/attestation) with location/recipient/purpose/access/maximum lifetime or explicit termination condition; observed metadata purpose/retention/disclosure; independent relay-key protection and explicit replacement procedure; deletion assurance/scope/maximum deadlines/key destruction/ledger retention and unprovable-copy limits. Disclose all lower quotas/rates and applicable per-chain allocation rules without publicly identifying a chain. Actual authenticated chain max_bytes MUST follow the disclosed rule; clients display it before first upload and provide a way to report a discrepancy and pause for corrected disclosure/renewed consent. The free-text Markdown policy is displayed to users; arbitrary prose is not automatically interpreted. Clients MUST validate privacy.json against privacy.schema.json and §7.13 semantic/signature/binding rules, display its structured values alongside the explanation, and pause on missing/invalid mandatory fields or observable health/quota inconsistencies. Operator prose must agree with these signed fields.

No protocol-wide numeric quota, retention days or operator copy lifetime is inferred. If backups/copies do not exist, state that explicitly instead of omitting fields. If max_bytes=null, state no configured quota rather than infinite physical storage. backup-durable still requires at least daily backups and restore testing at least every 90 days (§17.1). backup-expiry MUST disclose a finite maximum expiry/deletion deadline and supply its specific delete_after_ms; no finite commitment means that assurance cannot be advertised. crypto-shred applies only to separately encrypted operator storage-key copies, never the E2EE keys the relay lacks (§17.7). Minimal anti-resurrection/public authority evidence retained after deletion is disclosed separately; it is not permission to resurrect or retain deletable ciphertext indefinitely.

Every Markdown or structured-document change increments the signed public disclosure revision and requires renewed client consent; normal app upgrades/probes cannot consent for the user. Publish changes before their declared effective time, disclose how existing data/copies are affected, and do not describe previously retained copies as erased merely by changing text. A policy, consent record or operator promise is not cryptographic proof of actual storage/erasure and cannot authorize plaintext/root/share uploads, automatic history deletion, pin reset, automatic key/origin replacement or limits above §0/§17.8. A relay lacking complete published deployment values/document is nonconformant for public use; the Open Questions do not permit leaving mandatory disclosure unresolved at deployment.

## 18. Device Lifecycle

### 18.1 QR Offer, SAS and Approval

An active approving device creates a live offer (§10.7) only after local user intent to add a device. The QR has exactly `protocol:"pallasync/3",relay_origin,chain_id,generation,parameters_hash,epoch_hash,request_id,offer_nonce,expires_at_ms,admin_public_key:b64u(32),approver_device_id:uuid4,approver_device_public_key:b64u(32),approver_device_kex_public_key:b64u(32),approver_device_record_hash:b64u(32)`. Pin these keys/hashes from the physical QR; the full DeviceRecord is transferred separately so encrypted metadata/extensions do not make the offer exceed QR capacity. Its origin is HTTPS. This is a physically authenticated offer, not a bearer capability granting membership. The subject obtains current signed parameters, epoch history and the full approver DeviceRecord/approval chain over the QR-authenticated local session, verifies their pinned hashes/public keys, checks protocol, origin, expiry, approver certificate/signature and parameter/epoch bindings, generates fresh signing/KEX keys and a fresh device ID, and submits its self-signed EnrollmentRequest. The subject must compare full chain/approver identity displayed on both devices when accepting an unfamiliar QR; no trust is derived from an unauthenticated relay lookup alone.

Both sides compute X25519 between the approver's device_kex key and prospective device_kex key, reject all-zero output, then derive a visual SAS:

```text
T = JCS({"offer":QR_object,"request_hash":object_hash(EnrollmentRequest)})
SAS = lower_hex(SHA-256("PALLASYNC-ENROLL-SAS-v3\0" || X25519_shared_secret || T)[0:6])
```

Display the 12 hexadecimal characters in three groups of four on both devices. A user compares them over the local/independent channel and confirms on both devices; no auto-confirmation or relay-provided “match” is accepted. The shared secret is session-only and zeroized. The exact offer/request is committed by the certificate's request_hash; replacing a subject key/request invalidates the confirmation. One offer binds exactly one subject request; rejection/expiry consumes it. Repeated mismatches require a fresh offer, not repeated guesses within one approval session.

After SAS confirmation the approver signs EnrollmentCertificate, transfers it and enough epoch ciphertext to allow subject metadata construction over the confirmed session, and the subject signs the final DeviceRecord. This transfer MAY use the same physical/local user channel; no unlisted relay message mailbox is assumed. The control payloads are the exact §7 signed certificate, envelope and DeviceRecord objects serialized as JCS; implementations MUST provide a transfer channel that preserves these values and their pinned hashes. Interactive QR/file/local-channel selection is a product choice; no arbitrary relay chat response substitutes for user SAS confirmation. The approver submits the complete approval payload; relay verifies offering identity, certificate, self-signature and policy. Subject retrieves its own current envelope using P, verifies commitment, persists protected keys and acknowledges; only then is it active. For peer historical enrollment the approver must possess eligible old keys or use a separate mnemonic-holder session. SAS and HPKE do not confer mnemonic/root authority.

### 18.2 Registry and Self-Healing Decision Table

Allowed transitions: unknown → pending_keys on approved certificate; pending_keys → active on current-key acknowledgement; active or pending_keys → revoked in an atomic revocation epoch; revoked has no transition back. An ID/key rotation creates a fresh subject, not reuse of revoked identity. The relay losing a registry entry is not evidence that prior revocation never occurred.

| Observed condition | Required action | Automatic enrollment allowed? |
|---|---|---|
| Active, local key matches, current envelope present | Normal sync; verify checkpoint before writes. | No enrollment needed. |
| pending_keys | Fetch own envelope, verify commitment, keys/ack. | Only acknowledgement of already approved subject. |
| DEVICE_REVOKED or signed epoch revokes self | Stop ordinary reads/writes/approvals, retain historical verification/local data; inform user. | No. New approval with fresh device keys/ID required. |
| CHAIN_NOT_FOUND with intact local data | Suspend uploads; inspect origin/log/backup; require admin recovery or verified relay migration. | No. |
| Registry missing self, parameters/head otherwise consistent | Fetch signed enrollment/epoch history; ask enrolled peer or mnemonic holder to restore/reapprove fresh identity. | No unconditional re-registration. |
| DEVICE_KEY_MISMATCH or ID conflict | Quarantine conflicting identity, preserve evidence, new keys/ID after explicit approval. | No. |
| Envelope missing / EPOCH_STALE | Verify epochs; fetch/resend authorized envelope; rebuild only unaccepted outbox. | No enrollment unless certificate is actually absent. |
| LOG_ID_MISMATCH / restore rollback | Stop cursor advancement; compare pinned prefix/source checkpoint; repair or re-seed. | No. |
| Valid authenticated chain-deletion ledger | Stop all chain work; erase local chain state per §17.7. | No; deleted deterministic identity cannot be resurrected. |
| Unverified 410 / unconfirmed deletion notice | Suspend, preserve keys/data, obtain authorization proof. | No. |
| Lost local private keys | Generate fresh keys/ID and perform peer or mnemonic enrollment. | No self-signed replacement under an existing ID. |
| Root compromise | New mnemonic/new chain, §13.8. | No same-root repair. |

Transient network/503 failures do not enter unknown/missing states. Fresh enrollment approval is user intent, not an implicit response to every 404. Audit each self-heal attempt/result where it can be uploaded; unavailable chains keep a protected local audit queue. The protocol does not require a foreground confirmation for every ordinary retry/key acknowledgement.

### 18.3 Audit Collection

Enrollment, revocation, rotation, quarantine, self-healing, compaction and migration actors enqueue `pallasync.audit/3` events referencing signed object hashes and results (§8.6). Audit event creation MUST NOT be a precondition for an emergency revocation/delete when a malicious relay refuses writes. Emit it as soon as the current authorized chain is writable; if deletion removes the chain, retain an optional local user receipt rather than resurrect an audit collection. Audit can be replayed/idempotently indexed like other encrypted events. Do not put plaintext audit details in server problem bodies or enrollment metadata.

### 18.4 Revocation and Historical Records

Revocation simultaneously removes server access, excludes the device from the new epoch and replaces the secret. An honest relay refuses all revoked-device tokens and new record/envelope submissions, including old-epoch records. Every client learns revocation from the signed epoch chain and registry evidence, not from a mutable status string alone. Already accepted records from before revocation remain historically eligible and participate in K unless explicitly deleted/cleared; revocation is not retroactive application deletion. Historical verification keys/certificates remain available.

For a pinned known log, pre-revocation acceptance evidence validates old records. A malicious relay can invent an unobserved “accepted before revocation” position for a valid old signed record; no device signature contains a trusted acceptance time. Such a record has authenticity but unproven acceptance eligibility. Clients mark it `C_ACCEPTANCE_UNPROVEN` pending independent pre-revocation checkpoint/export proof; they MUST NOT infer historical acceptance from client created_at_ms or a fresh unsigned receipt alone. A first-time replay trusts the selected authenticated snapshot/history source for completeness/acceptance ordering; unconditional P-2 against all malicious relay views is not claimed. Revoked devices can read their own retained ciphertext/keys offline and cannot be forced to erase them.

### 18.5 Device Key Rotation

Generate new random Ed25519/X25519 keys and UUIDv4; enroll the new subject by peer or mnemonic approval; acknowledge its envelope; then commit reason key_rotation revoking the old ID and delivering a fresh epoch to retained members/new subject. A compromised old device must not be the sole approving authority; use mnemonic or another trusted enrolled device. Move unaccepted user intents to the new identity with fresh records/stamps; do not copy old private keys or re-sign historical accepted records. Retain old verification history; local old private keys may be destroyed after new identity/bootstrap is verified and old outbox uncertainty is resolved. The transition is auditable and does not change the mnemonic or chain_id.

### 18.6 Set Creation, Distribution and Activation

Opt-in setup requires a mnemonic-holder session and explicit selection of independent devices/offline media. Require `2<=t<n<=255`, recommend 2-of-3 including one offline medium, explain n−t tolerable losses and that t distinct leaked pieces plus a blob expose root. Existing occupied holders and backup-cloned instances do not become additional slots. Peer enrollment grants no share automatically; offering a share afterward requires separate setup/consent and full-set regeneration when holder membership changes.

1. Generate RMS, new set/share IDs and independent coefficients; canonicalize Recovery Secret, compute fingerprint, encrypt its padded blob and generate all raw shares transiently (§5.6). Build/admin-sign the immutable manifest and prepared status. No secrets are written to a staging file.
2. For each selected holder establish confirmed local SAS (§7.11.5). Send only its share plus manifest/blob. Holder generates independent local RSWK/key ID, wraps/checks its piece, returns wrap_proposal; dealer matches bindings/commitment and admin-signs the exact proposal. Holder verifies unchanged signed record, unwraps/checks again, atomically persists its single protected package and returns persisted/readback acknowledgement. The dealer never receives RSWKs.
3. For an offline slot, a trusted issuing/reader endpoint performs equivalent wrapping under its fresh RSWK, protects RSWK with separate offline credential (§7.11.4), obtains admin signature and outputs the designated encrypted physical medium. Readback verifies hashes, credential unwrap, commitment and package signatures; the issuer then zeroizes its temporary offline piece/key/package. It does not retain a second persistent share.
4. Obtain verified acknowledgements for all n distinct slots. Perform an explicit user-confirmed threshold test using t stored holders and live SAS, validate the fingerprint/derived identity, then admin-sign active status and distribute its public status chain to all holders. Activation/test does not authorize an unrelated root operation. If one medium is temporarily unavailable, setup remains prepared rather than claiming fully distributed redundancy.
5. Queue recovery_share_set_created (or rotated) and permitted holder metadata events; zeroize RMS, all raw share/coefficient buffers and root inputs on success/failure/cancel. Existing encrypted holder artifacts remain, with correct prepared/active status.

Creation cannot secretly resume by persisting RMS. After partial failure, use a fresh mnemonic-holder session, retire the prepared set and regenerate fresh material. Replacing a holder's existing package is atomic locally; a whole multi-device replacement is not a distributed atomic transaction. During replacement show `rotation_incomplete`, H per set and the temporary loss of recoverability. Preserve prior public hashes/status evidence; do not retain multiple secret packages on one device to hide this gap. A completed new set is marked active only after all distribution/readback/test guards; then sign old retired status referencing it and destroy accessible old RSWKs/packages/media. Unreachable old copies remain a disclosed risk (§20.4).

### 18.7 Loss, Compromise and Disablement

H counts currently usable distinct pieces of the same set whose credentials/storage are available. If `H>t` recovery remains possible with margin; `H=t` means **the next loss makes recovery unavailable**; `H<t` means recovery is **already unavailable** through that set. H=1 is always below threshold. Do not automatically reconstruct mnemonic upon loss. Mark the loss in local public status/UI, enqueue recovery_share_lost and recommend replacing the set while either direct mnemonic input or a usable threshold is still available. Lost pieces cannot be recovered from the relay.

A suspected holder/backup leak is treated as a leaked piece. Mark the set compromised locally immediately, stop ordinary ceremonies from using it, emit recovery_share_compromised and require full regeneration under fresh RMS/set/polynomials/blob/RSWKs using direct mnemonic input or a separately uncompromised set. If direct input is unavailable and the compromised set is the only usable source, an **explicit emergency ceremony** MAY use it solely to migrate to new root inputs/new chain; show the compromise warning and do not reactivate it as safe. This narrowly authorized path requires all usual SAS/input/checkpoint checks and the user-selected new-chain migration. Routine ceremonies return C_RECOVERY_SHARE_COMPROMISED.

Fresh RMS prevents mixing old and new pieces; it does not revoke an old threshold and old blob that still reconstruct the unchanged mnemonic. Erase accessible copies and disclose possible retained copies. If t pieces or the mnemonic/passphrase may have leaked, same-root regeneration is insufficient: migrate to a new mnemonic/new chain (§13.8). Unknown theft plus intact OS protection cannot prove no leak; conservatively treat a possibly extracted piece as compromised. Revoking a device/rotating epochs does not revoke its retained recovery share.

Disablement requires a mnemonic-holder session to sign retired status, propagate public retirement where reachable and erase local packages/RSWKs/accessible offline media. It MUST NOT claim adversarial copies were revoked. Without root input, a user may locally erase their own package or record suspected compromise/loss; this does not sign authoritative set-wide retirement or establish root authority. Audit is optional delivery, not a precondition for security action.

### 18.8 Holder Replacement, Key Rotation and Backup Exposure

Holder membership, t,n and immutable share bindings never change in place. Replacing a device/medium, adding/removing a holder or changing thresholds creates a complete new set through §18.6. Do not clone the old piece/RSWK onto the new device. Ordinary DeviceRecord key rotation preserves physical holder_instance_id and its existing package's original certified device binding until explicit set replacement; it grants no new shares. Recommend replacement after peer enrollment or device replacement; require it after compromise or possible OS/cloud backup inclusion. Treat cloud/OS-backup copies as possible leaks, delete reachable copies and display the root-compromise threshold limit. One imported clone is still one index, never independent recovery capacity.

### 18.9 Recovery UI and Local Deletion Guards

Every conformant client MUST provide availability/provisioning status, explicit setup/create, t/n configuration, per-holder distribution/readback status, offline output/credential guidance, explicit ceremony/operation selection, collection counts, live SAS on both endpoints, success/failure/cancel results and loss/leak regeneration screens. Display protection class and independent physical-holder warning before accepting a device. No secret is shown in log/crash/screenshot previews; SAS is public session authentication data. Any user-requested plaintext mnemonic viewing is outside automatic recovery and requires explicit secure handling; the protocol never saves it.

| Condition | Required user-visible behavior |
|---|---|
| `t=1`, `n=t`, `n<t` or `n>255` | Refuse invalid setup, C_RECOVERY_PARAMETER_INVALID. |
| Duplicate physical holder or occupied device without explicit replacement | Refuse second stored piece; do not inflate counts. |
| No offline medium | Warn that common device-loss events can destroy every piece; user may knowingly proceed. |
| H=t | Show remaining threshold and next-loss warning. |
| `H<t`, including H=1 | Show recovery already unavailable for this set; direct mnemonic or another valid set needed. |
| Backup inclusion/suspected leak | Show compromised set, mandatory replacement and threshold/root migration consequences. |
| Rotation interrupted | Show prepared/incomplete state and usable capacity of each set; no false “protected” completion. |
| SAS mismatch/unconfirmed/expired | Abort share transmission, preserve stored packages, display retry with fresh session. |
| Relay migration proposal | Show candidate origin; no background origin change, authorization/token, export or data upload before explicit selection and validation (§17.6). |
| Unverified deletion/410 | Show deletion_unverified, suspend sync, retain keys/packages/local data; no auto-erasure. |

Verified logical chain deletion targets its local share package/RSWK and encrypted blob too, after retaining optional **public** deletion evidence separately (§17.11). Manual local erase requires explicit user action, irrespective of an untrusted network hint. Chain deletion cannot erase unreachable offline media or copies held by another endpoint.

## 19. Errors and Quarantine

### 19.1 RFC 9457 Format

Problems use `application/problem+json` and [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457). REQUIRED fields: `type:string` (this profile uses `"about:blank"`), `title:string` (reason phrase for status), `status:integer` (actual HTTP status), `code:string` (catalogue), `retryable:boolean`, `server_time_ms:ms`. OPTIONAL: `detail:string` (sanitized ≤1,024 bytes), `instance:string` (request path without sensitive query), `context:object` containing only defined retry/reconciliation values. Unknown extension problem members may be ignored as RFC 9457 extensions; they MUST NOT be used as signed protocol authority. This exception to §3.1 J-6 applies only to error bodies. Human text is not a decision key. Problems MUST NOT include token/private material, decrypted identifiers or untrusted plaintext echoed from a record.

```json
{"type":"about:blank","title":"Conflict","status":409,"code":"EPOCH_STALE","retryable":true,"server_time_ms":1791684000000,"detail":"Fetch the current epoch and rebuild unaccepted records.","instance":"/pallasync/v3/chains/<chain_id>/records","context":{"epoch":4,"epoch_hash":"<b64u32>"}}

They are hints to fetch signed evidence, not substitutes for it. A deleted-chain problem includes deletion_id/receipt_hash and directs the client to GET deletion. Per-item rejections use §10.6's compact format, referencing this catalogue instead of repeating full problems. Standard infrastructure failures without valid JSON remain transport failures; clients never parse an HTML 410 as authenticated deletion.

### 19.4 Recovery from Quarantine

Resolve missing evidence first; fetch through a fresh authorized request or independently authenticated peer/export. Re-run the entire pipeline on immutable original bytes/value; successful revalidation/applied mark and cursor update are transactional and idempotent. A sender cannot “fix” a signed object in place; replacement uses a new ID and explicit audit reference. Invalid originals remain excluded with a resolution record. For forks/rollback/equivocation, suspend affected writes and destructive actions until user/admin resolves the trusted branch via re-seed or new chain; never choose by larger relay_seq/wall clock. Export evidence before deleting it. A knowingly excluded corrupt record is an explicit unresolved gap in verified coverage and blocks compaction of that prefix unless an authorized verified-state migration creates a new generation with documented exclusions. A client can continue applying independent valid records while showing partial status; it MUST NOT claim complete convergence with a different accepted input set.

## 20. Limits and Fundamental Constraints

### 20.1 What the Protocol Cannot Protect

No guarantee of relay/network availability, perpetual storage, honest quota enforcement, truthful backup/deletion claims, complete delivery to an isolated device or fresh initial recovery from a single malicious relay exists. Epoch links detect contradiction with known authenticated evidence, not hidden unseen tails. A full valid signature authenticates the author, not factual correctness of its application body, semantic completeness of its snapshot or honest recovery-envelope creation. Authorized malicious devices can write destructive application events, raise Lamport toward exhaustion and exercise their enabled approval/rotation permissions. E2EE does not protect plaintext/keys on a compromised endpoint, screenshots, user-exported plaintext, IP/traffic analysis or secrets typed into malicious software.

### 20.2 Copies, Revocation and Mnemonic Limits

Revocation prevents honest-relay access and possession of newly distributed secrets. It cannot erase ciphertext, plaintext, screenshots, old epoch secrets or mnemonics that a device/adversary already retained. Retention key erasure and relay deletion provide no retroactive erasure guarantee against such copies. Mnemonic/passphrase compromise is full root-authority compromise, including retained recovery envelopes; root identity can only be changed by a new mnemonic/passphrase and new chain. “Mnemonic-only recovery” restores keys/authority only if an accessible relay/export still has required ciphertext/envelopes or a verified replacement snapshot; the mnemonic is not a backup of application data. A nonempty lost BIP39 passphrase is as unrecoverable as a lost mnemonic unless that exact input was already provisioned into a usable recovery set (§20.4).

### 20.3 Resource and Interoperability Limits

Unbounded history grows disk, index, backup/export and bootstrap work. Paging bounds memory/UI work; it does not bound total storage or eliminate O(history) verification/state transfer. Default retention without automatic deletion therefore depends on sufficient client/relay capacity and can enter §16.4's visible blocked states. No protocol silently discards acknowledged data to simulate infinite capacity. Hard integer, record, operation and snapshot-part bounds remain. In 3.x, a snapshot exceeding 65,536 parts is unsupported: retain/replay the required full log, show the limit, and do not publish partial state as a complete snapshot or prune its uncovered prefix. Existing numeric fields and Palleria `/3` external ID bodies above 2^53−1 are likewise unsupported: reject authoring/invalid plaintext without rounding, string substitution, truncation or changing the current schema. A future larger snapshot/ID representation needs a separately published version decision consistent with §0; no current 3.x extension or policy exception exists. OQ-05 concerns that future design, not permission to exceed today's limits. Independently implemented clients converge on the same validated input and authenticated snapshot semantics; they cannot guarantee identical state while one relay withholds records or clients make different explicit trust/exclusion decisions.

---

### 20.4 Recovery and Relay-Attestation Limits

Shamir recovery mitigates loss of already provisioned root inputs; it never invents forgotten/unprovisioned inputs. Loss of every holder or fewer than t usable distinct pieces (including lost unlock credentials) prevents share recovery; direct mnemonic/passphrase remains usable if retained separately. Holders are not application-data backups: no available ciphertext/export/epoch envelopes or verified replacement snapshot means root recovery alone cannot recover data. A compromised collector/reader can steal all pieces/root inputs it handles. One medium/device cloned many times is still one share and correlated loss/leak; authenticated software cannot prove independent physical possession.

New RMS/coefficients/set IDs prevent combining old and new sets but cannot invalidate a retained old threshold plus its old blob while the mnemonic/passphrase are unchanged. Status flags, device revocation, epoch rotation, same-chain re-seeding and share regeneration cannot revoke that root. Possible threshold leakage requires new mnemonic/new chain. Similarly, passphrase changes change chain identity and require new shares; a blob-only replacement with a new RMS is undecryptable with old shares. Deleting a chain does not erase unreachable offline packages or adversarial copies of root inputs. Byte-buffer zeroization cannot prove absence from compromised runtime/OS memory; endpoint compromise remains outside E2EE protection.

Relay receipts/transparency/deletion signatures prove what a pinned key stated. They do not prove honest storage, physical deletion, total event delivery, real timestamp ordering or absence of unseen split views. Independent checkpoint exchange provides contradiction detection when evidence meets; no global availability/consensus or federation is introduced. Linear proof verification grows with its suffix, so probes/exports must stream and may stay pending. Extra logs increase disk/backup cost and traffic metadata; no unlimited-storage promise is made.

## Appendix D. Conflict Resolution Examples

These examples use A, B, R and S as defined in Appendix C.7. Every operation belongs to an authenticated eligible record; arrival time is immaterial. Keys are written as tuples for readability, but snapshots use the K-array JSON representation. A winner can remain stored while invisible.

### D.1 Equal-Lamport Delete Wins

| Input | K | Entity |
|---|---|---|
| B upsert query `cat` | (42,0,B,S,0) | cat |
| A delete query `cat` | (42,1,A,R,0) | cat |

Final register is the delete tombstone and cat is absent, even though B's UUID bytes sort after A. Receiving the upsert again changes nothing. A fresh upsert with Lamport 43 can recreate cat; a repeated Lamport-42 upsert cannot.

### D.2 Scoped Clear and Offline Upsert

Collection is view_history/3. A clear(seen) has K=(50,1,A,R,0). B upsert seen:7 at (50,0,B,S,0) is suppressed; B upsert viewed:7 at (51,0,B,S,1) is live because the clear does not match viewed. A future seen:7 upsert at (52,0,A,R,1) is live. Adding clear(all) at Lamport 53 suppresses both scopes below it. No event affects search history. Clear does not renumber rows or erase the winning-register evidence.

### D.3 Same Entity, One Row and Move to Front

Search events in two records are: R/A alpha upsert at Lamport 10 op0, beta at 11 op1, alpha at 13 op2; S/B gamma at Lamport 12 op0. The winning rows display alpha (K13), gamma (K12), beta (K11). Alpha's original K10 event is retained in the immutable archive but is not another row. Reverse arrival and ten duplicate deliveries yield the same three rows/order. A display timestamp newer than all four does not alter the comparison.

### D.4 Same Fractional Key and Concurrent Move

Favorite tags left/right have keys `1` and `2`. A and B concurrently insert distinct tags x and y with key `11`; the order is left, the two inserts sorted by ascending K/entity_id, right. Later A moves x after right by a higher-Lamport upsert with key `3`, while B deletes x at the same Lamport; delete wins and x is absent. A key change alone cannot defeat rank-one at a Lamport tie.

### D.5 Projection Eviction Does Not Delete History

For a small **illustrative projection of N=2**, three live search entries have K10(a), K11(b), K12(c). The hot projection is c,b and floor=(K11,b); a remains a live archived entry. A delete of c changes the projection to b,a and moves the floor down to (K10,a). A delayed losing upsert for a does not move it. Setting user limit back to null shows all live archived rows subject to the separate safety projection. No synchronized delete/clear is emitted for eviction. Production ceilings remain §16.1's values; N=2 is not a replacement constant.

### D.6 Tombstone After Snapshot and Replay

A snapshot covers sequence 100 and stores q's delete at K70 plus a clear watermark K65. A delayed duplicate q upsert K60 from the covered prefix is ignored by exact ID/hash evidence; even if processed through a full replay, K70 wins. A newly accepted eligible q upsert K71 is visible. A snapshot that retained only live rows and discarded K70 could incorrectly revive K60 and is therefore invalid. Prefix pruning preserves rejecting evidence and removed-ID hashes.

### D.7 Out-of-Order Author Sequences and Epochs

A valid record with device_seq 9 arrives before seq 8. Apply its authenticated operations by K, track the missing authored range, and do not use device_seq as an entity conflict key. When 8 arrives, compare 9's prev_record_hash and clear the gap if consistent; entity winners remain max K. A mismatch is C_DEVICE_EQUIVOCATION. If 8 was an unaccepted cancelled outbox item, the gap can remain as declared author evidence without inventing a missing accepted log receipt. A later epoch cannot retroactively make a previously unaccepted revoked-device record eligible.

### D.8 Retention Policy Merge

A writes a search retention policy (limit 100, stop false) at K80, B writes (limit null, stop false) at K81, and an old finite policy arrives last. K81 wins and the logical archive has no configured automatic deletion. A policy is not an entity/clear; it never removes tombstones or archived events. A later stop=true preference pauses new local entities only at the safety ceiling; remote valid records are still received. Two clients with identical winners and policy compute the same finite projection/floor.
